## 1층의 데이터 흐름

```
../Plitsoft-SDP (CLI 저장소, 읽기만)
      │  휠을 빌드해 격리 환경에서 실행       │  pack.yaml + _legal/ 을 읽음
      ▼                                       ▼
scripts/capture-cli-output.mjs         scripts/export-pack-meta.mjs   (임시: CLI 가 직접 내보낼 때까지)
      │                                       │
      ▼                                       ▼
contract/cli-current/*.json            data/pack-meta.json
      │                                       │
      └──────────────┬────────────────────────┘
                     ▼
        src/lib/report/parse.ts        결과 JSON 확인 (브라우저에서도 돈다)
        src/lib/report/view-model.ts   정책별·규칙별로 묶고 상태를 정함
                     ▼
        src/components/result/         결과 화면 부품
                     ▼
        /view  /demo  /policy          빌드하면 out/ 에 정적 파일
```

- `/view`: 사용자가 고른 JSON 파일을 브라우저에서 읽어 같은 부품으로 그린다. 서버로 보내지 않는다.
  브라우저에서 도는 부품에는 팩 메타데이터 전체를 주지 않는다. 쪽(서버 부품)이 팩 판과 정책의 id·제목·조문 이름만 골라
  props 로 넘긴다(`src/lib/pack/index.ts` 의 `packIndex`). 전체를 불러오면 화면에 싣지 않는 팩 작성자 메모까지 JS 묶음에
  실려 나간다. 조문 도감 주소는 데이터를 불러오지 않는 `src/lib/pack/href.ts` 에서 만든다(`tests/bundle.test.ts`).
- `/demo`: 빌드할 때 `contract/fixtures` 의 합성 코드와 `contract/cli-current` 의 결과를 읽는다.
- `/policy/<이름>`: `data/pack-meta.json` 의 정책마다 한 쪽. 빌드할 때 만들어진다. 주소의 이름은 정책 id 의 점을
  빼기표로 바꾼 것이다(`kr.pipa.22-2` → `kr-pipa-22-2`, `src/lib/pack/index.ts` 의 `policySlug`). 점이 든 경로는 Next 가
  링크에서 끝 슬래시를 떼어 일부 정적 호스팅에서 열리지 않는다.

## 결과 JSON 을 읽는 두 가지 계약

| 계약 | 알아보는 법 | 무엇이 다른가 |
|---|---|---|
| `cli-0.3` | `schema_version` 이 없다 | CLI 가 지금 내는 것. 발견(검토 필요·판단 보류)만 있다 |
| `v1-draft` | `schema_version: "report/1-draft"` | 웹의 요청안. 정책별 요약과 충족 근거 위치가 있다 |

`cli-0.3` 결과에서는 발견이 없는 정책이 "충족 근거 발견"인지 "적용 신호 없음"인지 정책별로 알 수 없다(전체 판정 단위
수 `run.units` 만 안다). 그래서 "발견 없음"으로 보이고 그 이유를 화면에 적는다. `v1-draft` 는 CLI 가 아직 내지 않으므로
`contract/samples-v1-draft/` 의 예시로만 본다. 판 번호가 없는 결과에 `run.policies` 가 있어도 쓰지 않는다.

## 발견 하나의 단위

- 발견 하나 = 정책 × 규칙 × 파일. 함수 단위 규칙(`scope: anchor`)이면 정책 × 규칙 × 함수다. kr-core 의 규칙은 지금
  모두 파일 단위다.
- 같은 파일·같은 줄에 규칙이 다른 발견이 둘 있을 수 있다(예: `night-push.main` 의 제50조 제4항은 시작 표기와 수신거부
  두 규칙이 같은 줄에 나온다). 서로 다른 의무이므로 하나로 접지 않고 규칙 이름과 함께 보인다.
- 파일 단위 규칙에서 `line` 은 적용 조건이 처음 맞은 줄이다. 판정 대상은 파일 전체다. 그 줄이 문제의 줄이라는 뜻이 아니다.
- 함수 단위 규칙의 판정 구역은 셋으로 갈린다(CLI README 의 "함수 단위 판정", CLI 소스 `report/outcome.py` 의 Finding).
  감싸는 함수가 있으면 그 함수(`region`), 함수 안팎에 섞여 있을 때의 함수 밖 줄(`region: null`, `top_level: true`),
  감싸는 함수가 없으면 파일 전체(`region: null`, `top_level: false`). `src/lib/report/scope.ts` 가 이것을 "판정이 본
  범위"로 옮긴다. 함수 단위인데 `top_level` 이 없는 결과는 어느 쪽인지 짐작하지 않고 "알 수 없음"으로 둔다.
- `line` 이 `null` 인 발견도 있을 수 있다(적용 조건이 맞은 자리를 남기지 않았을 때. CLI 소스 `evaluate/engine.py` 의
  `_anchor`. 수집본에는 없다). 화면은 파일 이름만 적고 줄 번호 이야기를 하지 않는다.
- `unsatisfied_alternatives` 에는 참이 아니라고 판정된 대안만 실린다. 값(`value`)은 `false` 이거나, 파일 일부를 읽지
  못했거나 엔진이 조건을 끝내지 못했을 때의 `unknown` 이다(수집본에는 `false` 만 있다. `unknown` 은 CLI 소스
  `evaluate/engine.py` 의 `static_value`, `_unsatisfied` 에서 확인했다). 판정에 넣지 않은 AI 대안과, 참이지만 약해서 풀지
  못한 대안은 목록에 없고 `decision_path` 의 문장에만 나온다.

## 결과 화면에서 발견을 묶는 법 (`view-model.ts` 의 `RuleGroupView`, `components/result/PolicyCard.tsx`)

정책 카드 → 규칙 묶음 → 발견 줄(경로·줄, 판정이 본 범위, 상태) 순서로 그린다.

- 규칙 묶음은 먼저 봐야 할 상태가 위에 오고, 같은 상태 안에서는 결과에 나온 순서다(CLI 는 팩의 규칙 순서로 낸다).
- 접는 단위는 규칙 묶음이다. 같은 규칙의 발견이 3곳(`SHOWN_PER_RULE`)보다 많을 때만 앞의 3곳을 먼저 보이고 나머지를
  접는다. 규칙이 다른 발견은 서로 다른 의무라서 접지 않는다. 한 정책에 발견이 많아도 규칙이 모두 다르면 전부 보인다.
- 먼저 보이는 3곳은 웹이 고른다(CLI 가 대표 위치를 주지 않는다. `docs/cli-requests.md` 의 R6). 먼저 봐야 할 상태,
  파일, 줄 순서다. 접힌 곳에 다른 상태가 섞여 있으면 묶음 머리에 상태별 개수를 적어 가려지지 않게 한다.
- 파일 순서는 글자 코드 순서다(UTF-16 코드 단위. 대문자가 소문자보다 앞이고 한글은 로마자 뒤다). 보는 사람의 언어
  설정을 따르는 비교(`localeCompare`)는 쓰지 않는다. 그 순서는 언어마다 달라서(체코어는 "ch" 를 "h" 뒤에 두고,
  한국어는 한글을 로마자 앞에 둔다) 같은 결과 파일인데도 먼저 보이는 3곳이 사람마다 달라진다.
- 발견 줄을 펼치면 "확인되지 않은 적법한 대안(대안마다 질문 → 고치는 법) → 판정을 끝까지 하지 못한 이유 → 판정 경로"가
  이 순서로 나온다. 묶음마다 첫 발견만 펼쳐 둔다. 같은 규칙의 다른 곳은 대안이 대개 같아서 한 줄로 둔다.
- 질문이나 고치는 법이 결과에 없으면(`null`) 없다고 적는다. 같은 규칙의 다른 대안이나 팩에서 끌어오지 않는다.
  판정 경로는 CLI 가 낸 문장을 그대로 보인다. 판정 경로가 비어 있으면 실려 있지 않다고 적는다.
- 발견 줄에는 닫혀 있어도 줄 번호 옆에 판정이 본 범위가 보인다("파일 전체 판정", "함수 12~34행 판정", "함수 밖 판정",
  "판정 구역 알 수 없음"). 줄 번호가 문제의 줄처럼 읽히지 않게 하기 위해서다. 펼친 안쪽의 첫 줄에 같은 내용을
  문장으로 적는다. 문구는 `src/lib/report/scope.ts` 에 있다.
- 함수 단위 규칙이면 같은 파일의 여러 함수도 같은 방식으로 센다(발견의 단위가 함수이기 때문이다). 같은 파일 안에서는
  줄 순서다.
- 줄 전체가 펼침 단추(`summary`)다. 경로는 복사해 가는 글이라 고를 수 있어야 한다. 끌어서 고르면 줄이 여닫히지 않고,
  두 번·세 번 이어 눌러 골라도 처음 상태로 돌아온다(`components/result/FindingSummary.tsx`, 판단은 `selection.ts`).
  스크립트가 돌기 전이나 꺼진 브라우저에서는 어디를 눌러도 여닫힌다.
- 같은 파일·같은 줄에 규칙이 다른 발견이 있으면 줄의 글이 같아진다. 눈에는 묶음 머리가 규칙을 말해 주고, 화면
  낭독기에는 줄마다 규칙 이름을 보이지 않게 붙여 구분되게 한다.
- 경로는 "/" 뒤에서 줄을 바꾼다. 파일 이름 하나가 한 줄보다 길면 이름 가운데서도 바뀐다. 확장자와 ":줄"은 한
  덩어리로 묶어 줄 번호만 다음 줄에 홀로 남지 않게 한다.
- 화면에서만 드러나는 것(가로 넘침, 접힌 곳이 실제로 가려지는지, 글을 골라도 여닫히지 않는지)은 `npm run check` 가
  보지 못한다. 그려 낸 HTML 의 모양만 본다. 브라우저 자동화는 `ROADMAP.md` 의 8번에서 넣는다.

## 빈 결과 화면 (`components/result/ReportSummary.tsx` 의 `EmptyReport`, `lib/report/examined.ts`)

발견이 0인 결과에만 보인다. "0이어도 법적 문제가 없다는 뜻이 아니다"(`SITE.zeroIsNotClearance`) 바로 아래, 정책 카드
위에 둔다. 접어 두지 않는다. 발견이 없다는 것만으로는 무엇을 봤는지 알 수 없기 때문이다.

- **검사한 것.** 결과에 실린 수를 그대로 옮기고, 그 수가 무엇이 아닌지를 옆에 적는다. 다른 수에서 짐작해 채우지 않는다.
  설명은 같은 화면의 다른 글과 맞아야 한다. 화면의 다른 곳을 가리킬 때는 그곳의 이름을 그대로 부르고, 접혀 있으면
  펼치라고 적는다.

  | 줄 | 값 | 함께 적는 것 |
  |---|---|---|
  | 검사한 파일 | `run.files` | 결과에는 수만 있고 목록도, 검사한 범위(저장소 전체인지, 바뀐 파일이나 일부 경로만인지)도 없다(R14). 범위를 좁혀 돌린 결과가 전체를 본 결과와 모양이 같아서(아래), 그 수가 전체를 본 수처럼 읽히지 않게 둘 다 없다고 적는다. 어느 범위였는지 짐작해 적지 않는다. "어느 파일인지 모른다"고도 적지 않는다(데모의 코드 상자와 충족 근거 위치에 파일 이름이 보인다). 0이면 "검사한 파일이 없어서 발견도 없다"를 눈에 띄게 적는다. 수가 없으면 "알 수 없음" |
  | 판정 단위 | `run.units` | 모든 정책을 합친 수다. `cli-0.3` 에는 정책별 수가 없다는 한계, 0일 때의 뜻, AI 가 적용되지 않는다고 답해 빠진 판정이 이 수에 없다는 것(아래) |
  | 검사하지 않은 파일 | `run.skipped` 의 수 | 있으면 그 파일들의 코드는 보지 못했다고 눈에 띄게 적고, 위의 "다 보지 못한 것" 표를 이름으로 가리킨다(목록은 그 표에 있다). "없음"은 CLI 가 이름을 적어 알린 파일이 없다는 뜻이라고 적고 "이 도구가 보지 못하는 것"을 가리킨다 |
  | 정책 | 정책의 수 | 어디서 센 수인지(아래). 목록은 바로 아래의 정책 카드다 |

- **`cli-0.3` 의 한계.** 정책별로 "적용 신호를 본 곳"을 알 수 없다. 정책 카드는 모두 "발견 없음"으로 같고, 결과마다 다른
  것은 전체 판정 단위 수뿐이다(`plain.main` 은 0, `kids-signup.fixed` 는 1). 그래서 그 수 옆에 "모든 정책을 합친 수이고
  이 출력 형식에는 정책별 수가 없다"고 적는다. 어느 정책의 것인지 아는 것은 AI 가 푼 경고(`run.ai_cleared`)에 실린
  단위뿐이다.
  - 수가 0이면 정책별 수도 모두 0이라 "정책별 수가 없다"는 한계가 아니다. 그때는 "0이므로 어느 정책에서도 판정한 곳이
    없다"고 적고, 그런데도 카드가 "발견 없음"(충족인지 미적용인지 구분할 수 없다)인 까닭을 함께 적는다: 정책별 요약이
    없어 카드는 판정 단위가 있는 결과와 같은 설명으로 보인다. 카드를 "적용 신호 없음"으로 바꾸지는 않는다(관문 G1 의 일).
  - AI 가 적용되지 않는다고 답해 빠진 판정(`run.ai_dismissed`)은 단위 수에 들어 있지 않다. CLI 는 적용 조건이 '모름'일
    때만 AI 에게 묻고, '아니오'를 받은 단위를 뺀 뒤에 센다(CLI 소스 `evaluate/engine.py` 의 evaluate,
    `evaluate/planner.py`). 빠진 판정이 있으면 수 옆에 "N건은 이 수에 들어 있지 않다"와 아래 목록의 이름을 적는다
    (`v1-draft` 에서도. `run.units` 는 같은 필드다). 그때는 수가 0이어도 판정한 곳이 없다고 적지 않는다. 판정자를 켠
    결과인데 그 목록이 실려 있지 않을 때도 적지 않는다(`ReportView.aiDismissedKnown`).
- **`v1-draft`.** 카드마다 `run.policies[].units` 를 적는다(발견이 있는 정책에도). 발견이 없는 카드에는 상태의 설명을 늘
  적는다. 충족 근거 위치가 함께 실려 있어도 적는다. 카드는 결과에 나온 정책(요약, 발견, AI 가 푼 경고)만 그린다. 요약이
  그 결과를 만든 팩의 모든 정책이므로(스키마의 `run.policies`), 이 사이트의 팩에만 있는 정책을 "발견 없음"이나
  "알 수 없음" 카드로 채워 넣지 않는다.
- **정책의 수.** `cli-0.3` 결과에는 정책 목록이 없다. 결과의 팩 판이 이 사이트의 팩과 같을 때만 그 팩에서 세고, 다르면
  "알 수 없음"이다. `v1-draft` 는 결과에 실린 요약의 수다(`ReportView.policyCount`). 정책별 수가 적힌 카드의 수와 같다.
  요약이 비어 있으면 "0개"를 눈에 띄게 적고 카드는 없다. 요약에 없는 정책이 AI 가 푼 경고에만 나오면 그 카드가 따로
  있다고 적는다. 이 두 경우는 손으로 만든 결과에서만 생긴다.
- **이 도구가 보지 못하는 것.** JS/TS 가 아닌 파일, 목록 없이 빠지는 JS/TS 파일(이름으로 가리는 폴더, git 이 무시하는
  파일, 하위 모듈처럼 저장소 안에 따로 든 다른 git 저장소, 심볼릭 링크, 읽을 권한이 없는 폴더), 검사한 범위 밖의 파일,
  서버·인프라 설정, 데이터에만 있는 동의 상태. 문구는 `SITE.notSeen` 에 있다. 도구가 보는 범위에 관한 사실만 적고 법에
  관한 판단은 적지 않는다. 빠지는 것을 늘어놓은 글은 "그 밖에는 다 봤다"로 읽히고, "검사하지 않은 파일: 없음"의 풀이도
  이 목록을 가리킨다. 그래서 CLI 가 이름을 알리지 않고 빼는 것은 확인한 대로 모두 적고, 새로 확인하면 더한다. 대상
  언어는 팩이 정하므로(이 사이트의 팩은 JS/TS), 다른 판의 팩으로 만든 결과에는 그 팩이 다른 언어도 검사하는지 알 수
  없다고 덧붙인다.
  - 목록 없이 빠지는 JS/TS 파일의 다섯 가지는 항목 아래에 한 줄씩 나눠 적는다(`NotSeenItem.cases`). 한 문단에 담으면
    375px 에서 14줄이었다.
  - 발견이 있는 결과에도 같은 목록이 있다. 커버리지 보기의 표 아래에 접어 둔다(아래 "커버리지 보기"). 그때는 첫
    문단만 다르다(`SITE.notSeen.leadWithFindings`).
  - 검사한 범위 밖의 파일은 조건으로 적는다("바뀐 파일만 검사하거나 일부 경로만 검사할 때는 …"). 결과에 범위가 없어서
    이 결과가 범위를 좁힌 결과인지 전체를 본 결과인지 알 수 없기 때문이다. 어느 쪽이라고도 적지 않고, 범위가 결과에
    실려 있지 않다는 것을 함께 적는다.
- CLI 0.3.0.dev0(`8ae72d8`)을 합성 폴더에 돌려 확인한 것(2026-10-06~07). 이름을 댔다거나 범위를 좁혔다고 적은 것
  말고는 폴더를 통째로 검사했을 때다.
  - JS/TS 가 아닌 파일(`.py`, `.json`, `.html`, `.yaml`, `.vue`, `.env`)과 `node_modules`·`dist`·`build`·`vendor`·`coverage`
    아래 파일은 검사하지 않고 `run.skipped` 에도 싣지 않는다. 폴더는 내용이 아니라 이름으로 가리고, 경로의 어느
    마디든 본다(`src/features/coverage/` 아래도 빠진다. CLI 소스 `discover.py` 의 `SKIP_DIRS`).
  - git 저장소 안이면 git 이 무시하는 파일도 그렇게 빠진다. `.gitignore` 로 무시했든 `.git/info/exclude` 나 전역 무시
    목록(`core.excludesFile`)으로 무시했든 같다. CLI 가 파일 목록을 `git ls-files --cached --others --exclude-standard`
    로 받기 때문이다(CLI 소스 `discover.py` 의 `_git_files`). 무시되지 않은 파일은 커밋하지 않았어도 검사하고, 무시된
    파일도 이름을 대서 주면 검사한다. 무시 규칙에 맞아도 이미 추적 중인 파일은 git 이 무시하지 않으므로 검사한다.
  - git 저장소 안에 따로 든 다른 git 저장소의 파일도 그렇게 빠진다. 하위 모듈(submodule), 제 `.git` 을 가진 폴더(커밋이
    없어도), 저장소 안에 만든 `git worktree` 가 모두 같다. git 이 그 폴더를 한 줄(`packages/inner`)로만 내는데, 그 줄은
    확장자가 없어 대상 언어가 아닌 파일처럼 버려진다. stderr 에도 알리지 않는다. 그 폴더를 이름을 대서 주면 검사하고,
    검사하는 폴더가 git 저장소 안이 아니면 그 안에 든 저장소도 보통 폴더처럼 검사한다.
  - 검사하는 폴더 안의 심볼릭 링크는 따라가지 않는다. stderr 에 개수만 알리는데, 이름에 JS/TS 확장자가 붙은 링크만
    센다(CLI 소스 `discover.py` 의 `admit` 이 확장자를 먼저 본다). 그래서 파일을 가리키는 링크(`src/signup.ts`)는
    개수에 들고, 폴더를 가리키는 링크(`linked`)는 그 아래 파일이 빠지는데도 stderr 에 나오지 않는다. 가리키는 파일이나
    폴더가 검사하는 폴더 안에 있으면 그 파일은 제 경로로 검사한다. 검사할 곳으로 링크를 직접 대면 따라간다.
  - 읽을 권한이 없는 폴더(`chmod 000`, `chmod 111`) 아래 파일도 그렇게 빠질 수 있다. 검사하는 폴더가 git 저장소 안이
    아니거나 git 이 추적하지 않는 파일이면 목록 없이 빠지고 stderr 에도 나오지 않는다. git 이 추적하는 파일이면
    다르다. 폴더에 들어갈 수는 있으면(`111`) 검사하고, 들어가지도 못하면(`000`) CLI 가 내부 오류(종료 코드 2)로 끝나
    결과가 나오지 않는다(Python 3.12 로 돌렸을 때). 늘 빠지는 것이 아니라서 화면에는 "빠질 수 있습니다"라고 적는다.
    읽을 권한이 없는 파일은 이와 달리 `run.skipped` 에 실린다.
  - 범위를 좁혀 돌린 결과에도 범위가 실리지 않고, 범위 밖의 파일은 `run.skipped` 에도 없다. 가입 코드(전체를 검사하면
    검토 필요 1건)는 그대로 두고 다른 파일 하나만 고쳐 스테이징한 git 저장소에서 `scan --staged`,
    `scan --diff <기준 브랜치>`, 그 파일만 이름을 대서 준 검사는 모두 `files: 1`, 발견 0건, `skipped: []`,
    `coverage_complete: true` 다. 실행 시간만 빼면 수집본 `plain.main` 과 글자까지 같다. 하위 폴더 하나만 주거나 하위
    폴더에서 돌려도(경로를 주지 않으면 현재 폴더를 검사한다), git 저장소가 아닌 폴더에서 파일 하나만 줘도 같다. 범위는
    `--staged`·`--diff` 일 때 stderr 한 줄("스테이징된 파일 1개를 검사합니다.")에만 나오고, 경로로 좁혔을 때는 거기에도
    없다. SARIF 에도 없다. 스테이징된 파일이나 바뀐 파일이 없으면 `files: 0`, `engine: null` 인 결과가 나온다.
  - `run.skipped` 에 실리는 것은 축소·번들 파일, `.mts`, UTF-8 이 아닌 파일 같은 것이다. 검사할 파일이 없으면
    `files: 0`, `engine: null`, `coverage_complete: true` 인 결과를 낸다.

  `const email = ;`)를 넣으면 그 파일이 `run.unparsed` 에 실리고 `run.files` 에도 세어진다. 발견은 그대로 나온다.
  - 적용 조건이 참으로 남으면 발견의 이유(`untested_reasons`)에 `parse-error` 가 없다. 대안의 값이 `unknown` 이 되어
    판단 보류로 바뀔 뿐이다. 까닭은 판정 경로의 문장("파일 일부가 파싱되지 않음")에만 나온다. `parse-error` 는 적용
    조건이 '모름'일 때만 붙는다(CLI 소스 `evaluate/engine.py` 의 evaluate).
  - 고치기 전 광고 푸시 코드(평소 발견 2건)는 5건이 된다. 평소에는 적용되지 않던 전자우편 규칙 셋이 적용 여부 '모름'으로
    나온다. "판단 보류로 남았을 수 있습니다"는 이런 발견을 가리킨다.
  - 글자만 보는 대안은 그대로 판정된다. 고치기 전 채팅 코드의 결과물 표시 규칙은 일부를 읽지 못한 파일에서도 검토
    필요로 남았다.
  - 구문 오류가 있어도 `run.unparsed` 에 실리지 않는 파일이 있다. `calcKoreanAge(form.birthDate;`, `if (age < 14 {` 처럼
    괄호 하나가 빠진 가입 코드는 `unparsed: []`, `coverage_complete: true` 로 나왔다(엔진이 오류 없이 넘어갔다).
    "일부를 읽지 못한 파일: 없음"은 결과에 실린 목록이 비었다는 뜻이다.
- **엔진이 끝내지 못한 파일.** 실제 시간 초과는 일으키지 못했다. 엔진을 감싼 스크립트(`POLICYPACK_SEMGREP`)로 엔진
  출력을 고쳐 CLI 가 무엇을 내는지 봤다. 엔진의 동작은 흉내이고, 그 뒤 CLI 의 동작은 실제다.
  - 조건 하나의 시간 초과(그 조건의 매치를 지우고 `rule_id` 가 붙은 Timeout 오류를 넣음): 그 파일이 `run.incomplete`
    에 실린다. 그 조건에 걸린 발견은 적용 여부가 참에서 '모름'이 되고 이유에 `engine-incomplete` 가 붙는다. 판정은
    바뀌지 않는다. 이 코드에서 그 발견은 약한 대안 때문에 시간 초과가 없어도 판단 보류다. 줄은 12행에서 15행이 되고
    (남은 적용 조건이 맞은 줄), 지문은 그 줄 둘레의 코드로 만들므로 함께 달라진다. 같은 파일의 다른 발견은 검토 필요
    그대로이고 판정 경로에 "엔진이 이 파일에서 규칙을 끝내지 못함"만 붙는다.
    - `tests/fixtures/incomplete-coverage.json` 이 이 출력이다. 검사한 합성 폴더는 `contract/fixtures` 의 코드로
      만들었다: `plain/main` 의 `src/math.ts`, `night-push/fixed` 의 `src/marketing/campaign.ts`, `kids-signup/main` 의
      `src/auth/signup.ts` 에 위의 쓰다 만 함수(`return email;` 과 `}` 까지 네 줄, 빈 줄 하나)를 import 아래에 넣은 것,
      `var a=1;` 한 줄짜리 `src/lib/chart.min.js`. 끼워 넣은 것은 `kr.network-act.50-3` 의 `send-call` 조건이
      `campaign.ts` 에서 낸 매치 1개를 지우고 더한 Timeout 오류 하나다. 폴더와 엔진을 감싼 스크립트는 저장소에 없다
      (`ROADMAP.md` 의 "사람 결정이 필요한 것").
  - 파일 하나의 시간 초과(`rule_id` 없는 Timeout 오류): 정책 신호가 없는 파일인데도(평소 발견 0건) 팩의 규칙 9개가
    모두 판단 보류로 나온다(끝나지 않은 조건은 거짓이 아니라 '모름'이라서다). 시간 초과만으로 판정이 달라지는 것은
    이 출력에서 본다.
  - 어느 파일인지 모르는 오류(경로 없는 Fatal error): `run.engine_errors` 에 "[Fatal error] …" 문장이 실리고, 함께
    검사한 파일 셋이 모두 `run.incomplete` 에 실린다. 일부를 읽지 못한 파일도 거기에 함께 실린다.
    - 실린 문장은 엔진의 문장 그대로가 아니다. CLI 가 오류 종류를 대괄호로 앞에 붙이고, 엔진 문장의 양끝 빈칸을 뗀
      뒤 앞 200자만 싣는다(CLI 소스 `static/parse.py`). 359자 문장을 넣으면 실린 것은 214자("[Fatal error] " 14자와
      앞 200자)이고 잘렸다는 표시는 없다. 안쪽의 줄바꿈·탭·이어진 빈칸은 남는다.

### `npm run check` 가 보지 못하는 것

그려 낸 HTML 의 모양만 본다. 좁은 화면에서 줄이 쌓이는지, 칸 머리가 보이지 않는지, 표가 넘치지 않는지, 접근성
트리에 표로 드러나는지, 오류 문장의 줄바꿈과 빈칸이 화면에 그대로 보이는지, 좁은 화면에서 줄 이름과 수의 글자
밑줄이 맞는지는 브라우저에서 손으로 쟀다(`ROADMAP.md` 의 3번, 8번).

## SARIF 에 있는 것과 없는 것

`--output-format sarif` 에는 발견·지문·판정 경로·대안(`results[].properties`)과 판정자·팩 판·AI 가 푼 것
(`invocations[0].properties`)이 있다. 판정 단위 수와 검사한 파일 수는 없다. 줄이 없는 발견은 1행으로 나온다.
SARIF 입력을 받을 때는 없는 것을 "알 수 없음"으로 보인다(`docs/cli-requests.md` 의 R11).

## 상태가 정해지는 규칙 (`src/lib/report/status.ts`, `view-model.ts`)

| 조건 | 상태 |
|---|---|
| 발견의 outcome 이 `needs-review-uncertain` | 판단 보류(모름) |
| outcome 이 `needs-review` 이고 `ai_pending` 이 비어 있지 않음 | 검토 필요 · AI 확인 전 |
| outcome 이 `needs-review` 이고 `ai_pending` 이 비어 있음 | 미충족 신호(검토 필요) |
| 발견이 없고, v1 요약에서 `compliant > 0` | 충족 근거 발견 |
| 발견이 없고, v1 요약이 있음 (그 밖) | 적용 신호 없음 |
| 발견이 없고, 요약도 없고, 결과의 팩 판이 사이트의 팩과 다름 | 알 수 없음 |
| 발견이 없고, 요약도 없음 (`cli-0.3`, 팩 판이 같음) | 발견 없음 (AI 가 푼 경고가 있으면 그 사실을 대신 적는다) |

정책의 상태는 그 정책의 위치들 가운데 가장 먼저 봐야 할 것이다.

카드로 그리는 정책은 계약마다 다르다. `cli-0.3` 은 이 사이트의 팩에 실린 정책 전부에 결과에 나온 정책을 더한 것이고,
`v1-draft` 는 결과에 나온 정책(요약, 발견, AI 가 푼 경고)뿐이다. 그래서 `v1-draft` 에서 발견도 요약도 없는 카드(표의
마지막 두 줄)는 요약에 없는 정책이 AI 가 푼 경고에만 나오는, 손으로 만든 결과에서만 생긴다.

## 2층 설계 요약 (아직 만들지 않는다)

확장 구상에서 정한 방향이다. 만들기 전에 사실을 다시 확인한다.

1. 허용목록에 있는 GitHub 계정만 로그인한다(신원만, 권한 요청 없음).
2. 서버가 기본 브랜치의 커밋을 고정한다.
3. 일회용 격리 환경(Vercel Sandbox, 서울 리전, 영속 저장 끔)을 만든다.
4. 그 안에서 저장소 압축 파일을 받고 JS/TS 파일만 푼다. 경로 조작·심볼릭 링크·크기 상한을 막는다.
5. 받은 뒤 네트워크를 모두 끊는다.
6. `policypack scan --output-format json`(판정자 없음)을 돌린다.
7. 코드가 들어 있지 않은 필드만 골라 저장한다.
8. 환경을 파기하고 파기 시각을 남긴다.

검사를 Vercel 함수 안에서 직접 돌리지 않는 이유는 남의 코드를 격리할 수 없기 때문이다. 가장 가까운 선례는
Vercel Labs 의 deepsec(GitHub App + Sandbox)이다. 이 층을 시작하려면 `output: "export"` 를 걷어 내야 하고,
그것은 관문 G2 와 사람의 결정이 있어야 한다.
