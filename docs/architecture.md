## 1층의 데이터 흐름

```
../Plitsoft-SDP (CLI 저장소, 읽기만)
      │  휠을 빌드해 격리 환경에서 실행       │  pack.yaml + _legal/ 을 읽음
      ▼                                       ▼
scripts/capture-cli-output.mjs         scripts/export-pack-meta.mjs   (임시: CLI 가 직접 내보낼 때까지)
      │                                       │
      ▼                                       ▼
contract/cli-current/*.json            data/pack-meta.json
      │                                       │
      └──────────────┬────────────────────────┘
                     ▼
        src/lib/report/parse.ts        결과 JSON 확인 (브라우저에서도 돈다)
        src/lib/report/sarif.ts        SARIF 를 결과 JSON 의 모양으로 옮김 (`/view` 에서 연 파일만)
        src/lib/report/view-model.ts   정책별·규칙별로 묶고 상태를 정함
                     ▼
        src/components/result/         결과 화면 부품
                     ▼
        /view  /demo  /policy          빌드하면 out/ 에 정적 파일
```

- `/view`: 사용자가 고른 결과 파일(JSON, SARIF)을 브라우저에서 읽어 같은 부품으로 그린다. 서버로 보내지 않는다
  (아래 "`/view`").
  브라우저에서 도는 부품에는 팩 메타데이터 전체를 주지 않는다. 쪽(서버 부품)이 팩 판과 정책의 id·제목·조문 이름만 골라
  props 로 넘긴다(`src/lib/pack/index.ts` 의 `packIndex`). 전체를 불러오면 화면에 싣지 않는 팩 작성자 메모까지 JS 묶음에
  실려 나간다. 조문 도감 주소는 데이터를 불러오지 않는 `src/lib/pack/href.ts` 에서 만든다(`tests/bundle.test.ts`).
- `/demo`: 빌드할 때 `contract/fixtures` 의 합성 코드와 `contract/cli-current` 의 결과를 읽는다.
- `/policy/<이름>`: `data/pack-meta.json` 의 정책마다 한 쪽. 빌드할 때 만들어진다. 주소의 이름은 정책 id 의 점을
  빼기표로 바꾼 것이다(`kr.pipa.22-2` → `kr-pipa-22-2`, `src/lib/pack/index.ts` 의 `policySlug`). 점이 든 경로는 Next 가
  링크에서 끝 슬래시를 떼어 일부 정적 호스팅에서 열리지 않는다.

## 결과를 읽는 세 가지 계약

| 계약 | 알아보는 법 | 무엇이 다른가 |
|---|---|---|
| `cli-0.3` | `schema_version` 이 없다 | CLI 가 지금 내는 JSON. 발견(검토 필요·판단 보류)만 있다 |
| `v1-draft` | `schema_version: "report/1-draft"` | 웹의 요청안. 정책별 요약과 충족 근거 위치가 있다 |
| `sarif` | `runs` 배열이 있다 | CLI 가 지금 내는 SARIF. `cli-0.3` 과 같은 것을 담되 판정 단위 수와 검사한 파일 수가 없다(아래 "SARIF 에 있는 것과 없는 것") |

`cli-0.3` 결과에서는 발견이 없는 정책이 "충족 근거 발견"인지 "적용 신호 없음"인지 정책별로 알 수 없다(전체 판정 단위
수 `run.units` 만 안다). 그래서 "발견 없음"으로 보이고 그 이유를 화면에 적는다. `v1-draft` 는 CLI 가 아직 내지 않으므로
`contract/samples-v1-draft/` 의 예시로만 본다. 판 번호가 없는 결과에 `run.policies` 가 있어도 쓰지 않는다.

## 발견 하나의 단위

- 발견 하나 = 정책 × 규칙 × 파일. 함수 단위 규칙(`scope: anchor`)이면 정책 × 규칙 × 함수다. kr-core 의 규칙은 지금
  모두 파일 단위다.
- 같은 파일·같은 줄에 규칙이 다른 발견이 둘 있을 수 있다(예: `night-push.main` 의 제50조 제4항은 시작 표기와 수신거부
  두 규칙이 같은 줄에 나온다). 서로 다른 의무이므로 하나로 접지 않고 규칙 이름과 함께 보인다.
- 파일 단위 규칙에서 `line` 은 적용 조건이 처음 맞은 줄이다. 판정 대상은 파일 전체다. 그 줄이 문제의 줄이라는 뜻이 아니다.
- 함수 단위 규칙의 판정 구역은 셋으로 갈린다(CLI README 의 "함수 단위 판정", CLI 소스 `report/outcome.py` 의 Finding).
  감싸는 함수가 있으면 그 함수(`region`), 함수 안팎에 섞여 있을 때의 함수 밖 줄(`region: null`, `top_level: true`),
  감싸는 함수가 없으면 파일 전체(`region: null`, `top_level: false`). `src/lib/report/scope.ts` 가 이것을 "판정이 본
  범위"로 옮긴다. 함수 단위인데 `top_level` 이 없는 결과는 어느 쪽인지 짐작하지 않고 "알 수 없음"으로 둔다.
- `line` 이 `null` 인 발견도 있을 수 있다(적용 조건이 맞은 자리를 남기지 않았을 때. CLI 소스 `evaluate/engine.py` 의
  `_anchor`. 수집본에는 없다). 화면은 파일 이름만 적고 줄 번호 이야기를 하지 않는다.
- `unsatisfied_alternatives` 에는 참이 아니라고 판정된 대안만 실린다. 값(`value`)은 `false` 이거나, 파일 일부를 읽지
  못했거나 엔진이 조건을 끝내지 못했을 때의 `unknown` 이다(수집본에는 `false` 만 있다. `unknown` 은 CLI 소스
  `evaluate/engine.py` 의 `static_value`, `_unsatisfied` 에서 확인했다). 판정에 넣지 않은 AI 대안과, 참이지만 약해서 풀지
  못한 대안은 목록에 없고 `decision_path` 의 문장에만 나온다.

## 결과 화면에서 발견을 묶는 법 (`view-model.ts` 의 `RuleGroupView`, `components/result/PolicyCard.tsx`)

정책 카드 → 규칙 묶음 → 발견 줄(경로·줄, 판정이 본 범위, 상태) 순서로 그린다.

- 규칙 묶음은 먼저 봐야 할 상태가 위에 오고, 같은 상태 안에서는 결과에 나온 순서다(CLI 는 팩의 규칙 순서로 낸다).
- 접는 단위는 규칙 묶음이다. 같은 규칙의 발견이 3곳(`SHOWN_PER_RULE`)보다 많을 때만 앞의 3곳을 먼저 보이고 나머지를
  접는다. 규칙이 다른 발견은 서로 다른 의무라서 접지 않는다. 한 정책에 발견이 많아도 규칙이 모두 다르면 전부 보인다.
- 먼저 보이는 3곳은 웹이 고른다(CLI 가 대표 위치를 주지 않는다. `docs/cli-requests.md` 의 R6). 먼저 봐야 할 상태,
  파일, 줄 순서다. 접힌 곳에 다른 상태가 섞여 있으면 묶음 머리에 상태별 개수를 적어 가려지지 않게 한다.
- 파일 순서는 글자 코드 순서다(UTF-16 코드 단위. 대문자가 소문자보다 앞이고 한글은 로마자 뒤다). 보는 사람의 언어
  설정을 따르는 비교(`localeCompare`)는 쓰지 않는다. 그 순서는 언어마다 달라서(체코어는 "ch" 를 "h" 뒤에 두고,
  한국어는 한글을 로마자 앞에 둔다) 같은 결과 파일인데도 먼저 보이는 3곳이 사람마다 달라진다.
- 발견 줄을 펼치면 "확인되지 않은 적법한 대안(대안마다 질문 → 고치는 법) → 판정을 끝까지 하지 못한 이유 → 판정 경로"가
  이 순서로 나온다. 묶음마다 첫 발견만 펼쳐 둔다. 같은 규칙의 다른 곳은 대안이 대개 같아서 한 줄로 둔다.
- 질문이나 고치는 법이 결과에 없으면(`null`) 없다고 적는다. 같은 규칙의 다른 대안이나 팩에서 끌어오지 않는다.
  판정 경로는 CLI 가 낸 문장을 그대로 보인다. 판정 경로가 비어 있으면 실려 있지 않다고 적는다.
- 발견 줄에는 닫혀 있어도 줄 번호 옆에 판정이 본 범위가 보인다("파일 전체 판정", "함수 12~34행 판정", "함수 밖 판정",
  "판정 구역 알 수 없음"). 줄 번호가 문제의 줄처럼 읽히지 않게 하기 위해서다. 펼친 안쪽의 첫 줄에 같은 내용을
  문장으로 적는다. 문구는 `src/lib/report/scope.ts` 에 있다.
- 함수 단위 규칙이면 같은 파일의 여러 함수도 같은 방식으로 센다(발견의 단위가 함수이기 때문이다). 같은 파일 안에서는
  줄 순서다.
- 줄 전체가 펼침 단추(`summary`)다. 경로는 복사해 가는 글이라 고를 수 있어야 한다. 끌어서 고르면 줄이 여닫히지 않고,
  두 번·세 번 이어 눌러 골라도 처음 상태로 돌아온다(`components/result/FindingSummary.tsx`, 판단은 `selection.ts`).
  스크립트가 돌기 전이나 꺼진 브라우저에서는 어디를 눌러도 여닫힌다.
- 같은 파일·같은 줄에 규칙이 다른 발견이 있으면 줄의 글이 같아진다. 눈에는 묶음 머리가 규칙을 말해 주고, 화면
  낭독기에는 줄마다 규칙 이름을 보이지 않게 붙여 구분되게 한다.
- 경로는 "/" 뒤에서 줄을 바꾼다. 파일 이름 하나가 한 줄보다 길면 이름 가운데서도 바뀐다. 확장자와 ":줄"은 한
  덩어리로 묶어 줄 번호만 다음 줄에 홀로 남지 않게 한다.
- 화면에서만 드러나는 것 가운데 `/view` 의 가로 넘침(375px, 접힌 채와 모두 펼친 채)은 브라우저 시험이 본다(아래
  "브라우저 시험"). 접힌 곳이 실제로 가려지는지, 글을 골라도 여닫히지 않는지는 아직 `npm run check` 가 보지 못한다.
  부품 시험은 그려 낸 HTML 의 모양만 본다(`ROADMAP.md` 의 8번).

## 빈 결과 화면 (`components/result/ReportSummary.tsx` 의 `EmptyReport`, `lib/report/examined.ts`)

발견이 0인 결과에만 보인다. "0이어도 법적 문제가 없다는 뜻이 아니다"(`SITE.zeroIsNotClearance`) 바로 아래, 정책 카드
위에 둔다. 접어 두지 않는다. 발견이 없다는 것만으로는 무엇을 봤는지 알 수 없기 때문이다.

- **검사한 것.** 결과에 실린 수를 그대로 옮기고, 그 수가 무엇이 아닌지를 옆에 적는다. 다른 수에서 짐작해 채우지 않는다.
  설명은 같은 화면의 다른 글과 맞아야 한다. 화면의 다른 곳을 가리킬 때는 그곳의 이름을 그대로 부르고, 접혀 있으면
  펼치라고 적는다.

  | 줄 | 값 | 함께 적는 것 |
  |---|---|---|
  | 검사한 파일 | `run.files` | 결과에는 수만 있고 목록도, 검사한 범위(저장소 전체인지, 바뀐 파일이나 일부 경로만인지)도 없다(R14). 범위를 좁혀 돌린 결과가 전체를 본 결과와 모양이 같아서(아래), 그 수가 전체를 본 수처럼 읽히지 않게 둘 다 없다고 적는다. 어느 범위였는지 짐작해 적지 않는다. "어느 파일인지 모른다"고도 적지 않는다(데모의 코드 상자와 충족 근거 위치에 파일 이름이 보인다). 0이면 "검사한 파일이 없어서 발견도 없다"를 눈에 띄게 적는다. 수가 없으면 "알 수 없음" |
  | 판정 단위 | `run.units` | 모든 정책을 합친 수다. `cli-0.3` 에는 정책별 수가 없다는 한계, 0일 때의 뜻, AI 가 적용되지 않는다고 답해 빠진 판정이 이 수에 없다는 것(아래) |
  | 검사하지 않은 파일 | `run.skipped` 의 수 | 있으면 그 파일들의 코드는 보지 못했다고 눈에 띄게 적고, 위의 "다 보지 못한 것" 표를 이름으로 가리킨다(목록은 그 표에 있다). "없음"은 CLI 가 이름을 적어 알린 파일이 없다는 뜻이라고 적고 "이 도구가 보지 못하는 것"을 가리킨다 |
  | 정책 | 정책의 수 | 어디서 센 수인지(아래). 목록은 바로 아래의 정책 카드다 |

- **`cli-0.3` 의 한계.** 정책별로 "적용 신호를 본 곳"을 알 수 없다. 정책 카드는 모두 "발견 없음"으로 같고, 결과마다 다른
  것은 전체 판정 단위 수뿐이다(`plain.main` 은 0, `kids-signup.fixed` 는 1). 그래서 그 수 옆에 "모든 정책을 합친 수이고
  이 출력 형식에는 정책별 수가 없다"고 적는다. 어느 정책의 것인지 아는 것은 AI 가 푼 경고(`run.ai_cleared`)에 실린
  단위뿐이다.
  - 수가 0이면 정책별 수도 모두 0이라 "정책별 수가 없다"는 한계가 아니다. 그때는 "0이므로 어느 정책에서도 판정한 곳이
    없다"고 적고, 그런데도 카드가 "발견 없음"(충족인지 미적용인지 구분할 수 없다)인 까닭을 함께 적는다: 정책별 요약이
    없어 카드는 판정 단위가 있는 결과와 같은 설명으로 보인다. 카드를 "적용 신호 없음"으로 바꾸지는 않는다(관문 G1 의 일).
  - AI 가 적용되지 않는다고 답해 빠진 판정(`run.ai_dismissed`)은 단위 수에 들어 있지 않다. CLI 는 적용 조건이 '모름'일
    때만 AI 에게 묻고, '아니오'를 받은 단위를 뺀 뒤에 센다(CLI 소스 `evaluate/engine.py` 의 evaluate,
    `evaluate/planner.py`). 빠진 판정이 있으면 수 옆에 "N건은 이 수에 들어 있지 않다"와 아래 목록의 이름을 적는다
    (`v1-draft` 에서도. `run.units` 는 같은 필드다). 그때는 수가 0이어도 판정한 곳이 없다고 적지 않는다. 판정자를 켠
    결과인데 그 목록이 실려 있지 않을 때도 적지 않는다(`ReportView.aiDismissedKnown`).
- **`v1-draft`.** 카드마다 `run.policies[].units` 를 적는다(발견이 있는 정책에도). 발견이 없는 카드에는 상태의 설명을 늘
  적는다. 충족 근거 위치가 함께 실려 있어도 적는다. 카드는 결과에 나온 정책(요약, 발견, AI 가 푼 경고)만 그린다. 요약이
  그 결과를 만든 팩의 모든 정책이므로(스키마의 `run.policies`), 이 사이트의 팩에만 있는 정책을 "발견 없음"이나
  "알 수 없음" 카드로 채워 넣지 않는다.
- **정책의 수.** `cli-0.3` 결과에는 정책 목록이 없다. 결과의 팩 판이 이 사이트의 팩과 같을 때만 그 팩에서 세고, 다르면
  "알 수 없음"이다. `v1-draft` 는 결과에 실린 요약의 수다(`ReportView.policyCount`). 정책별 수가 적힌 카드의 수와 같다.

  언어는 팩이 정하므로(이 사이트의 팩은 JS/TS), 다른 판의 팩으로 만든 결과에는 그 팩이 다른 언어도 검사하는지 알 수
  없다고 덧붙인다.

  - 검사한 범위 밖의 파일은 조건으로 적는다("바뀐 파일만 검사하거나 일부 경로만 검사할 때는 …"). 결과에 범위가 없어서
    이 결과가 범위를 좁힌 결과인지 전체를 본 결과인지 알 수 없기 때문이다. 어느 쪽이라고도 적지 않고, 범위가 결과에

  말고는 폴더를 통째로 검사했을 때다.

    아래 파일은 검사하지 않고 `run.skipped` 에도 싣지 않는다. 폴더는 내용이 아니라 이름으로 가리고, 경로의 어느

    파일도 이름을 대서 주면 검사한다. 무시 규칙에 맞아도 이미 추적 중인 파일은 git 이 무시하지 않으므로 검사한다.
  - git 저장소 안에 따로 든 다른 git 저장소의 파일도 그렇게 빠진다. 하위 모듈(submodule), 제 `.git` 을 가진 폴더(커밋이
    없어도), 저장소 안에 만든 `git worktree` 가 모두 같다. git 이 그 폴더를 한 줄(`packages/inner`)로만 내는데, 그 줄은
    확장자가 없어 대상 언어가 아닌 파일처럼 버려진다. stderr 에도 알리지 않는다. 그 폴더를 이름을 대서 주면 검사하고,
    검사하는 폴더가 git 저장소 안이 아니면 그 안에 든 저장소도 보통 폴더처럼 검사한다.
  - 검사하는 폴더 안의 심볼릭 링크는 따라가지 않는다. stderr 에 개수만 알리는데, 이름에 JS/TS 확장자가 붙은 링크만
    센다(CLI 소스 `discover.py` 의 `admit` 이 확장자를 먼저 본다). 그래서 파일을 가리키는 링크(`src/signup.ts`)는
    개수에 들고, 폴더를 가리키는 링크(`linked`)는 그 아래 파일이 빠지는데도 stderr 에 나오지 않는다. 가리키는 파일이나
    폴더가 검사하는 폴더 안에 있으면 그 파일은 제 경로로 검사한다. 검사할 곳으로 링크를 직접 대면 따라간다.

    아니거나 git 이 추적하지 않는 파일이면 목록 없이 빠지고 stderr 에도 나오지 않는다. git 이 추적하는 파일이면
    다르다. 폴더에 들어갈 수는 있으면(`111`) 검사하고, 들어가지도 못하면(`000`) CLI 가 내부 오류(종료 코드 2)로 끝나
    결과가 나오지 않는다(Python 3.12 로 돌렸을 때). 늘 빠지는 것이 아니라서 화면에는 "빠질 수 있습니다"라고 적는다.
    읽을 권한이 없는 파일은 이와 달리 `run.skipped` 에 실린다.
  - 범위를 좁혀 돌린 결과에도 범위가 실리지 않고, 범위 밖의 파일은 `run.skipped` 에도 없다. 가입 코드(전체를 검사하면
    검토 필요 1건)는 그대로 두고 다른 파일 하나만 고쳐 스테이징한 git 저장소에서 `scan --staged`,
    `scan --diff <기준 브랜치>`, 그 파일만 이름을 대서 준 검사는 모두 `files: 1`, 발견 0건, `skipped: []`,

    폴더에서 돌려도(경로를 주지 않으면 현재 폴더를 검사한다), git 저장소가 아닌 폴더에서 파일 하나만 줘도 같다. 범위는
    `--staged`·`--diff` 일 때 stderr 한 줄("스테이징된 파일 1개를 검사합니다.")에만 나오고, 경로로 좁혔을 때는 거기에도
    없다. SARIF 에도 없다. 스테이징된 파일이나 바뀐 파일이 없으면 `files: 0`, `engine: null` 인 결과가 나온다.
  - `run.skipped` 에 실리는 것은 축소·번들 파일, `.mts`, UTF-8 이 아닌 파일 같은 것이다. 검사할 파일이 없으면
    `files: 0`, `engine: null`, `coverage_complete: true` 인 결과를 낸다.

## `/view` (`components/viewer/ReportViewer.tsx`, `lib/report/open.ts`)

CLI 의 JSON 출력과 SARIF 출력을 연다. 파일 고르기, 끌어다 놓기, 합성 예시 고르기의 세 길이 있고 처음에는 합성 예시
하나가 열려 있다.

- **브라우저 안에서만 읽는다.** 고른 파일은 `File.text()` 로 읽어 메모리에만 둔다. 요청을 내보내지 않고 브라우저
  저장소에도 두지 않는다. 정책 카드의 조문 도감 링크는 프리페치를 끈다(`prefetch={false}`). 켜 두면 링크가 화면에
  들어올 때마다 요청이 나가고, 어느 정책에 발견이 있는지에 따라 그 차례가 달라진다. 머리의 링크(사이트 이름·결과
  보기·데모·조문 도감)는 어느 파일을 열든 같아서 그대로 둔다. 쪽을 열 때 미리 받는다(같은 사이트 안의 정적 파일이다).
  - 머리 링크의 프리페치는 쪽을 열 때 한 번으로 끝나지 않는다. 받아 둔 것이 낡으면(Next 의 기본값은 5분) 머리 링크가
    화면에 다시 들어올 때, 화면에 그대로 있었으면 그 위에 마우스를 올릴 때 다시 받는다. 가만히 두면 나가지 않는다.
  - 다시 받는 것도 같은 사이트의 정적 파일이다(HEAD 와 GET, 본문 없음). 무엇을 열었든 같은 요청이다. 아무것도 열지
    않은 창과 서로 다른 파일을 연 두 창에서 서버가 받은 메서드·주소·머리말이 글자까지 같았다(머리말은 쪽의 시계를
    돌려 견줬다). 연 파일의 이름이나 내용은 실리지 않는다.
  - 잰 것(2026-10-07, 헤드리스 Chrome 154. 시계를 돌리지 않고 기다렸다): 파일을 연 지 4분 30초 뒤에는 맨 위로 올려도,
    머리 링크에 마우스를 올려도 0건이었다. 5분 50초가 지난 뒤에는 기다리는 동안 0건, 맨 아래로 내려도 0건, 맨 위로
    올리자 12건(네 쪽마다 HEAD 하나와 `__next.….txt` 둘), 머리가 내내 화면 안이던 창에서는 링크 하나에 마우스를
    올리자 그 쪽의 3건이 나갔다. 쪽의 시계를 앞으로 돌려 보면 4분 55초에는 0건, 5분 5초에는 12건이다.
  - 파일을 연 뒤에는 누르기 전까지 요청이 없게 하려면 머리 링크의 프리페치도 꺼야 한다. 끌지는 정하지 않았다
    (`ROADMAP.md` 의 "사람 결정이 필요한 것").
- **잘못된 파일.** 읽지 못한 까닭을 적고, 그 아래에 이 뷰어가 여는 파일과 그것을 만드는 명령의 예(`SITE.scanExample`)를
  한 줄 적는다. 앞서 연 결과는 걷어 낸다(그 파일의 결과처럼 보이면 안 된다). CLI 는 결과를 표준 출력으로만 내므로,
  결과 파일은 사용자가 출력을 파일로 돌려 저장한 것이다. 그러다 생기는 잘못이 그대로 들어온다.

  | 넣은 것 | 알리는 말 |
  |---|---|
  | 빈 파일 | CLI 가 결과를 내지 못하고 끝났을 수 있다(오류로 끝나면 저장한 파일이 비어 있다) |
  | JSON 이 아닌 글 | 출력 형식을 주지 않은 글 출력이거나, 터미널의 다른 글이 함께 적힌 파일일 수 있다 |
  | 결과가 아닌 JSON (`package.json` 등) | `tool`, `run`, `findings` 가 모두 없다는 한 줄 |
  | 결과로 보이지만 모양이 다른 곳이 있는 파일 | 필드마다 한 줄. 5개(`SHOWN_ERRORS`)까지만 보이고 나머지는 수만 적는다 |
  | 다른 도구의 SARIF | 이 CLI 가 싣는 팩 판(`packDigest`)이 없어 읽지 않는다. CLI 의 이름에는 조사를 바로 붙이지 않는다(이름이 바뀔 수 있고, 받침에 따라 조사가 달라진다) |
  | `runs` 가 하나가 아닌 SARIF | 몇 개인지 적는다. 하나인데 객체가 아니면 수가 아니라 그 사실을 적는다 |
  | 10MB(`MAX_FILE_BYTES`)보다 큰 파일 | 읽지 않고 크기와 한도를 적는다 |
  | 폴더, 읽을 수 없는 파일 | 읽지 못했다 |
  | 파일 여럿 | 첫 파일만 보고 그렇다고 적는다. 읽기 전에 정해지는 말이라 "열었습니다"라고 적지 않는다(첫 파일을 읽지 못하면 바로 아래의 안내와 어긋난다) |

- **끌어다 놓기는 창 전체에서 받는다.** 드롭존 밖에 놓아도 그 파일을 연다. 받지 않으면 브라우저가 놓은 파일을 대신
  연다. Chrome 154 는 새 탭으로 연다(헤드리스에서 확인. 다른 브라우저는 보지 못했다). 파일을 끌 때만 나선다(끌고 있는
  것의 종류에 `Files` 가 있을 때). 글이나 링크를 끄는 것은 건드리지 않는다.
  - 끄는 동안 드롭존을 강조하고, 창 둘레에 표시(`.drop-frame`)를 그린다. 드롭존은 쪽의 위쪽에 있어서, 결과를 읽으며
    내려가 있으면 강조가 화면 밖이다. 표시는 창에 붙어 있고 끄는 것을 가로채지 않는다(`pointer-events: none`).
  - 놓지 않고 끝난 끌기는 브라우저가 알리지 않을 때가 있어서(헤드리스 Chrome 에서 개발 도구 통신으로 끌기를
    그만두게 해 보니 쪽에 아무 이벤트도 오지 않았다), `dragover` 가 0.8초(`DRAG_IDLE_MS`) 오지 않으면 두 표시를
    끈다. 창 밖으로 나간 것을 알려 오면(좌표가 창 밖인 `dragleave`) 기다리지 않고 끈다. 사람이 마우스로 끌 때
    브라우저마다 `dragover` 가 얼마나 자주 오는지는 재 보지 못했다(HTML 표준은 0.35초 안팎마다라고 적는다).
  - 파일 입력 위에 놓은 파일도 같은 길로 한 번만 연다.
- **파일로 연 뒤에는 제목이 보이게 한다.** 고르거나 놓아서 연 것은 그려진 뒤 제목이 창 안에 온전히 들어와 있지 않으면
  제목으로 스크롤한다. 아래로 내린 채 파일을 놓았을 때와 낮은 화면(320×568 에서는 제목이 화면 아래에 있다)에서,
  무엇이 열렸는지도 읽지 못했다는 안내도 보이지 않기 때문이다. 제목이 보이면 움직이지 않는다. 예시 고르기는
  스크롤하지 않는다(고르기 상자에 초점을 둔 채 넘겨 보는 동안 화면이 움직이면 안 된다).
- **키보드.** 파일 입력과 예시 고르기는 브라우저의 기본 부품(`input type="file"`, `select`)이다. Tab 으로 머리의 링크
  다음에 차례로 닿고, 파일 입력에서 Enter 나 Space 를 누르면 파일 고르기가 열린다. 예시는 글자를 쳐서 고르거나
  화살표로 고른다(화살표의 동작은 운영체제마다 다르다. 맥은 메뉴를 연다).
  - 초점은 고르던 자리에 둔다. 결과 쪽으로 옮기지 않는다(예시를 넘겨 보는 동안 초점이 옮겨 가면 안 된다). 대신
    무엇을 열었는지를 화면 낭독기에 알린다(`role="status"`. 화면에는 보이지 않는다). 발견 수는 알리지 않는다. 수만
    들으면 0건이 "볼 것이 없다"로 들리고(`commitments.md` 의 1), 맨 위 경고와 AI 가 푼 경고가 빠진다. 그것은 결과
    화면이 차례대로 말한다.
  - "열었습니다"는 결과 화면이 실제로 붙은 뒤에만 알린다. 읽지 못했을 때와 그리다 실패했을 때(오류 경계)는 알리지
    않고, 안내 상자가 스스로 알린다(`role="alert"`). 안내 상자는 열 때마다 새로 만든다. 같은 요소로 남으면 같은
    까닭으로 읽지 못한 파일을 잇달아 열었을 때 다시 알릴 것이 없다.
  - 파일 고르기 창을 열 때 입력을 비운다(고른 뒤가 아니다). 같은 이름의 파일을 다시 골라도 열리게 하기 위해서다.
    고친 뒤 다시 검사한 결과는 이름이 같다. 고른 파일의 이름은 입력에 남는다. 예시를 열거나 파일을 놓아서 열면
    입력을 비운다(입력에 남은 파일이 열려 있는 것이 아니다). 고르기 창을 열었다가 그만두면 입력은 비고 열어 둔
    결과는 그대로다. 무엇이 열려 있는지는 제목이 말한다.
- **다른 쪽에 다녀와도 연 것이 남는다.** 연 것은 이 탭의 메모리에 둔다(모듈 변수 `kept`. 브라우저 저장소가 아니다).
  같은 문서 안에서 다른 쪽에 다녀오면(정책 카드의 링크, 머리의 링크, 뒤로·앞으로 가기) 뷰어가 새로 붙고, 그때 이것을
  되살린다. 되살리지 않으면 기본 예시가 열리는데, 뒤로 왔을 때는 브라우저가 스크롤 자리를 되살려서 "합성
  예시입니다"가 화면 밖에 놓이고 보이는 것은 예시의 정책 카드다(4번 검토에서 봤다. 커밋된 판도 그랬다).
  - 되살린 것은 화면 낭독기에 다시 알리지 않는다. 펼치거나 접어 둔 줄은 처음 상태로 돌아가고, 파일 입력은 비어
    있다(다시 붙은 입력은 새 요소이고, 앞서 고른 파일을 거기에 다시 넣지 않는다).
  - 되살릴 때는 미뤄 그리지 않고 한 번에 그린다(붙을 때 높이가 정해져 있어야 브라우저가 되살리는 스크롤 자리가
    맞는다). 발견이 많은 결과에서는 그동안 멈춘다. 뒤로 와서 다 그려질 때까지 500건 0.07초, 2,000건 0.13초, 5,000건
    0.31초였고 CPU 를 4배 늦추면 0.14초, 0.45초, 1.1초였다(아래 표와 같은 방법으로 쟀다). 스크롤 자리는 모두 맞았다.
- **새로 고치면 기본 예시가 맨 위에서 열린다.** 문서를 다시 받으면(새로 고침. 주소로 연 다른 쪽이나 다른 사이트에
  다녀왔는데 브라우저가 문서를 통째로 되살리지 않았을 때) 메모리가 비어 기본 예시로 돌아간다. 이때도 브라우저는 앞서
  보던 스크롤 자리를 되살린다. 그래서 되살릴 것이 없이 붙었고 문서를 다시 받은 것이면(`performance` 의 navigation
  종류가 `reload`·`back_forward`) 맨 위에서 시작한다(`startAtTop`).
  - 붙을 때 한 번 올리는 것으로는 되지 않았다(Chrome 154 에서 서른두 번 해 보니 스물여섯 번은 되살린 자리로
    돌아갔다). 브라우저가 자리를 되살리는 때가 그 뒤일 수 있다. 문서를 다 받은 직후에 한 번 더 되살리고(앞서 보던
    자리가 기본 예시의 높이보다 깊으면 이때 처음 되살린다), 조문 도감 쪽에서 새로 고친 뒤 뒤로 오면(같은 문서 안의
    이동이다) 뷰어가 붙은 다음 화면을 그리면서 되살린다. 그래서 문서를 다 받고 0.5초(`RESTORE_WATCH_MS`)가 지날
    때까지 스크롤이 움직이면 다시 올린다. 사람이 무엇인가 하기 시작하면(휠, 손가락, 키, 누르기, 파일 끌어 오기)
    곧바로 그만둔다. 그렇게 한 뒤에는 같은 서른두 번이 모두 맨 위에서 끝났다.
  - 처음 찾아온 문서에서는 하지 않는다. 스크립트가 늦게 붙는 동안 읽어 내려간 사람을 끌어올리게 된다.
  - 스크립트가 붙기 전에는 브라우저가 되살린 자리가 잠깐 보인다(JS 묶음을 0.4초씩 늦게 주면 0.8초쯤).
  - 뒤로·앞으로 가기로 문서를 다시 받으면 브라우저는 폼 값도 되살린다. 그대로 두면 화면은 기본 예시인데 파일 입력
    옆에 앞서 고른 파일의 이름이 적히고, 예시 고르기는 스크립트가 붙어 다시 그려질 때까지 떠나기 전의 값("직접 연
    파일"이나 앞서 고른 예시)을 가리킨다. 그래서 두 부품에 `autocomplete="off"` 를 줘서 브라우저가 값을 기억하지 않게
    한다. Chrome 154 는 문서를 다 읽은 바로 뒤에 되살리고 쪽에는 이벤트를 보내지 않는다. 새로 고침에서는 되살리지
    않았다.
  - 브라우저가 문서를 통째로 되살릴 때(bfcache)는 메모리도 함께 돌아온다. 연 것, 입력의 파일 이름, 예시 고르기,
    스크롤 자리가 떠나기 전 그대로다. 그 기능을 켜고 띄운 헤드리스 Chrome 154 에서 봤다. 자동화 도구는 그 기능을 끄고
    띄우므로 브라우저 시험은 이 길을 보지 못한다.
- **발견이 많은 결과.** 결과 화면은 한 박자 늦게 그린다(`useDeferredValue`). 파일 고르기와 예시 고르기는 곧바로
  새 파일을 가리키고, 결과는 그 뒤에서 조금씩 그려진다. 그리는 동안 화면이 멈추지 않는다. 다 그려질 때까지 앞서 연
  결과가 남아 있는데, 0.2초가 넘으면 흐리게 해 아직 바뀌지 않았음을 보인다.

  | 발견 | 파일 | 다 그려질 때까지 | 그동안 가장 길게 멈춘 시간 | CPU 를 4배 늦추면 |
  |---|---|---|---|---|
  | 500건 | 0.9MB | 0.07초 | 0.04초 미만 | 0.2초, 멈춤 0.05초 |
  | 2,000건 | 3.5MB | 0.17초 | 0.04초 미만 | 0.5초, 멈춤 0.09초 |
  | 5,000건 | 8.7MB | 0.31초 | 0.04초 | 1.1초, 멈춤 0.19초 |
  | 5,700건 | 9.9MB | 0.35초 | 0.05초 | 1.2초, 멈춤 0.17초 |

  - 이 컴퓨터(애플 실리콘 맥)의 헤드리스 Chrome 154 에서 잰 값이다(2026-10-07). 멈춘 시간은 쪽 안에서 프레임과
    프레임, 작업과 작업 사이의 가장 긴 틈으로 쟀다. 발견은 팩의 규칙 아홉에 고루 나눈 것이다.
  - 한 번에 그리던 때(4번 전)에는 그리는 내내 멈췄다: 500건 0.05초, 2,000건 0.13초, 5,000건 0.28초. 4배 늦추면
    0.16초, 0.46초, 1.0초였다.
  - 발견은 접힌 곳까지 모두 문서에 들어 있다(1번에서 정한 그대로다. 접힌 줄도 제 안쪽을 가진다). 그래서 요소 수는
    발견 수에 비례한다(500건에 2만 2천 개, 5,000건에 21만 7천 개). 화면에 보이는 것만 그리는 방식으로 바꾸지 않았다.
  - 10MB 한도는 결과가 아닌 큰 파일을 통째로 읽지 않기 위한 것이다. 결과로는 발견 5,000건을 조금 넘는 크기이고,
    그보다 큰 결과는 재 보지 않았다. CLI 의 한도가 아니라 이 뷰어의 한도다.
- **합성 예시 목록에 SARIF 는 넣지 않는다.** CLI 의 SARIF 에는 팩 작성자 메모가 실려 있다(아래). 예시로 넣으면 그 글이
  JS 묶음에 실려 나간다(`tests/browser/out-files.test.ts` 가 막는다).
- **예시 고르기 상자가 본문 칸을 넓히지 않는다.** 뷰어의 칸을 `minmax(0, 1fr)` 로 정했다(`globals.css` 의 `.viewer`).
  고르기 상자는 줄을 바꾸지 못해서, 그냥 두면 상자가 칸보다 넓을 때 칸이 상자만큼 넓어진다. 320px 에서 칸은 280px 이고,
  상자의 제 너비는 이 컴퓨터의 글꼴로 276px, 나눔고딕으로 295px 이다. 그 줄을 빼면 나눔고딕에서 본문의 오른쪽 여백이
  20px 에서 5px 이 되고, 상자가 더 넓으면 쪽이 가로로 넘친다(상자의 글자를 20px 로 키우면 363px, 넘침 63px). 그 줄이
  있으면 상자가 칸에 맞춰 줄고 여백은 그대로다(2026-10-07, 헤드리스 Chrome 154).
  - 같은 규칙을 쓰는 `.opened`·`.demo` 의 칸도 함께 정해진다(규칙을 나누지 않았다). 그 둘에서는 지금 이 줄이 있으나
    없으나 화면이 같다(브라우저 안에서 그 칸만 처음 값으로 되돌려 견줬다). 시험이 보는 것은 `.viewer` 의 칸이다.
  - 바깥 칸(`main.wrap`. 모든 쪽이 함께 쓴다)은 정하지 않는다. 4번에서 처음에는 함께 정했는데, 어느 화면도 바꾸지 않아
    걷어 냈다. 뷰어의 칸이 0 까지 줄 수 있어서, 고르기 상자를 넓혀도 뷰어가 바깥 칸을 밀지 않았다. 바깥 것을 넣은
    빌드와 뺀 빌드에서 모든 쪽을(`/view` 는 파일 17개를 접은 채와 편 채로) 240~1280px 의 여섯 너비와 네 가지 글꼴(그대로,
    나눔고딕, 고르기 상자만 20px, 모든 글자 20px)로 열어 본문 안 요소의 자리와 크기를 견줬고 1,092번 모두 같았다.
- **예시의 이름에는 출처를 다시 적지 않는다**(`lib/samples.ts`). 화면은 이름과 출처를 이어 적는다(고르기 상자의 항목은
  "이름 · 출처", 제목은 "이름 (출처)"). 이름에 "(v1 초안)"을 한 번 더 적던 때는 320px 에서 고른 항목의 끝이 잘렸다.
  고르기 상자는 줄을 바꾸지 못한다. 지금 가장 긴 항목은 이 컴퓨터의 글꼴로 상자 276px(칸 280px)이다. 글꼴이 더
  넓으면 다시 잘릴 수 있다.
- 보지 못한 것: 운영체제의 실제 끌어다 놓기(파인더에서 끌기)와 파일 고르기 창(그만뒀을 때를 포함해), Safari·Firefox
  (스크롤 자리와 폼 값을 언제 되살리는지, `autocomplete="off"` 를 어떻게 다루는지, 고르기 상자가 칸을 넓히는지도
  Chrome 에서만 쟀다), 실제 휴대 기기, 화면 낭독기가 알림을 읽는지.

### 문자 부호화

- 결과 파일은 UTF-8 로 푼다. 글자 순서 표시(BOM)가 UTF-16 이면 그 부호화로 푼다. 그 밖의 파일(예: 한글을 CP949 로 적은
  파일)은 어느 부호화인지 짐작해 풀지 않고 "UTF-8 로 읽을 수 없는 파일"이라고 알린다(`lib/report/open.ts` 의 `decode`).
- 느슨하게 풀면(`File.text()`) 깨진 글자(U+FFFD)가 든 채로 결과처럼 그려진다. 정책 제목과 경로가 읽을 수 없는 글이
  된다(4번의 마지막 확인에서 봄). 풀었더니 그 글자가 실제로 들어 있는 UTF-8 파일은 그대로 연다.
- CLI 는 결과를 표준 출력으로만 내므로 파일의 부호화는 받아 적는 터미널에 달려 있다(`docs/cli-requests.md` 의 R16).
  시험: `tests/open.test.ts` 의 "UTF-8 이 아닌 파일", `tests/browser/view.test.ts` 의 "잘못된 파일을 넣었을 때".

## SARIF 에 있는 것과 없는 것 (`lib/report/sarif.ts`, `contract/schema/sarif.cli-0.3.schema.json`)

`--output-format sarif` 의 출력을 결과 JSON 의 모양(`Report`)으로 옮겨 같은 화면으로 그린다. 실린 것은 JSON 과 같게
옮기고, 실리지 않은 것은 채우지 않는다. 같은 검사의 SARIF 와 JSON 을 열면 발견 부분(발견 수, 정책 카드, 발견 줄과
그 안쪽)이 글자까지 같다(`tests/sarif.test.tsx`).

| 결과 JSON | SARIF 의 자리 | |
|---|---|---|
| `tool` | `tool.driver.name`, `version` | |
| `run.engine` | `tool.extensions[0]` | 엔진을 돌리지 않았으면 없다. 그때 JSON 은 `engine: null` 이다(아래 "검사할 파일이 없던 검사") |
| `run.judge` | `invocations[0].properties.judge` | 꺼져 있으면 JSON 은 `null`, SARIF 는 `"none"` 이다 |
| `run.pack_digest`, `ai_pending`, `ai_cleared`, `ai_dismissed`, `coverage_complete` | `invocations[0].properties` | |
| `run.skipped`, `unparsed`, `incomplete`, `engine_errors` | `invocations[0].toolExecutionNotifications` | 파일마다 알림 하나. 종류는 `descriptor.id` 로 가린다 |
| `run.units`, `run.files` | **없다** | "알 수 없음". 커버리지 보기의 줄 아래에 까닭을 한 번 적는다 |
| 발견의 `policy`, `rule` | `ruleId` (`정책/규칙`) | CLI 가 두 id 에 `/` 를 받지 않아 하나로만 나뉜다 |
| 발견의 `title`, `ask_developer` | `tool.driver.rules` 에서 `ruleId` 가 같은 규칙의 `shortDescription`, `help.text` | 질문이 없는 정책이면 CLI 가 질문 자리에 제목을 싣는다. 제목과 같으면 질문이 없는 것으로 둔다 |
| 발견의 `file`, `line` | `locations[0].physicalLocation` | 줄이 없는 발견도 1행으로 실린다(아래) |
| 발견의 `region` | `contextRegion` | 일부에만 실린다(아래) |
| 발견의 `top_level` | **없다** | |
| 발견의 `fingerprint` | `partialFingerprints["policypack/v1"]` | |
| 발견의 나머지(판정, 조문 이름, 판정 단위, 이유, 대안, 판정 경로) | `results[].properties` | |

- **1행.** CLI 는 줄이 없는 발견(`line: null`)을 SARIF 에 `startLine: 1` 로 싣는다. 그래서 SARIF 의 1행은 실제 1행인지
  줄이 없는 발견인지 알 수 없다. 화면은 1행으로 보이되, 펼친 안쪽에서 "줄 번호는 조문이 닿는다고 본 첫 줄"이라고
  적는 대신 그 사정을 적는다(`LocationView.lineUnsure`, `scope.ts`). 수집본에서 `genai-chat` 의 발견이 실제로 1행이다.
- **판정 구역.** `contextRegion` 은 줄이 그 구역 안에 있고 구역이 두 줄 이상일 때만 실린다. `top_level` 은 없다.
  그래서 함수 단위 판정인데 구역이 실리지 않은 발견은 "판정 구역 알 수 없음"으로 보인다(JSON 에서는 "파일 전체
  판정", "함수 밖 판정", 한 줄짜리 함수의 구역으로 갈리던 것이다). 파일 단위 판정은 `scope` 만으로 알아서 JSON 과 같다.
  구역이 실린 발견은 줄이 있는 발견이므로 1행이어도 위의 사정을 적지 않는다.
  - CLI 는 함수 단위 규칙의 판정 경로 첫 문장 끝에 구역을 글로 적는다(`[구역 12~34행]`, `[구역 함수 밖]`,
    `[구역 파일 전체]`. CLI 소스 `evaluate/engine.py`). 그 문장은 SARIF 에도 실려 화면에 그대로 보인다. 웹은 그 문장을
    해석해 구역을 만들지 않는다. 그래서 줄의 이름은 "판정 구역 알 수 없음"으로 두되, 펼친 안쪽에는 "알 수 없다"고
    잘라 적지 않고 "결과에 따로 실려 있지 않습니다. 아래 판정 경로의 문장을 보세요."라고 적는다(바로 아래에
    `[구역 파일 전체]`가 보이면 서로 어긋나 보인다). 판정 경로가 실려 있지 않으면 가리키지 않는다.
- **검사할 파일이 없던 검사.** CLI 는 검사할 파일이 없으면 엔진을 돌리지 않고 빈 결과를 낸다(CLI 소스 `cli.py` 의
  cmd_scan. `--diff` 로 돌려 바뀐 파일이 없을 때 CI 에 올라가는 빈 SARIF 가 이것이다). JSON 은 `files: 0` 이라 맨 위에
  "검사한 파일이 없습니다."가 뜬다. SARIF 에는 파일 수가 없고 엔진만 빠져 있다. 0개였다고 짐작해 적지 않고, 실린

## 브라우저 시험 (`tests/browser/`, `npm run test:browser`)

빌드된 `out/` 을 127.0.0.1 의 빈 포트에 띄우고, 이 컴퓨터에 깔린 Google Chrome 을 헤드리스로 열어 본다. 그려 낸
HTML 만 보는 부품 시험이 볼 수 없는 것을 본다. `npm run check` 의 차례는 lint → typecheck → 부품 시험 → build →
브라우저 시험이다. 이 컴퓨터에서 전체가 36초 안팎이고 그 가운데 브라우저 시험이 29초쯤이다(2분 안에 끝나야 한다.
`ROADMAP.md`).

- **도구.** `playwright-core` 하나를 개발 의존성으로 더했다(4번). 브라우저를 다루는 라이브러리이고, 시험을 돌리는
  것은 이미 쓰던 vitest 다(`vitest.browser.config.mts`). 배포물(`out/`)에는 들어가지 않는다.
- **브라우저를 내려받지 않는다.** `playwright-core` 는 브라우저를 함께 받지 않고, 시험은 깔려 있는 Chrome 을 쓴다
  (`channel: "chrome"`). Chrome 이 다른 자리에 있거나 Chromium 계열의 다른 브라우저를 쓰려면 `CHROME_PATH` 에 실행
  파일을 준다. 시험이 여는 쪽이 내보내는 요청은 127.0.0.1 의 그 서버로 가는 것뿐이다. 다른 곳으로 나가려는 HTTP
  요청과 쪽의 스크립트가 여는 WebSocket(어디로 가든)은 내보내지 않고 막은 뒤 실패로 적는다. 그 둘이 아닌 통신은 이
  시험이 가로채지 못한다(아래 "보지 못하는 것"). Chrome 이 스스로 뒤에서 하는 통신(갱신 확인, 동기화 등)은 끄는
  옵션으로 띄운다(`playwright-core` 가 그렇게 띄운다). 그것이 하나도 없는지는 이 시험이 보지 못한다. 어느 쪽이든
  사이트가 내보내는 요청이 아니라 개발 도구가 브라우저를 띄우면서 생기는 일이다.
- **Chrome 을 찾지 못하면 실패한다. 건너뛰지 않는다.** 건너뛰면 "연 파일을 어디로도 보내지 않는다"를 보는 시험 없이
  `npm run check` 가 통과한다. 그 시험은 1층의 약속을 보는 것이라, 보지 못했으면 통과라고 하지 않는다. 실패할 때
  무엇을 하면 되는지 적는다(Chrome 을 깔거나 `CHROME_PATH` 를 준다). Chrome 없이 나머지만 보려면 단계를 따로 돌린다
  (`npm run lint`, `npm run typecheck`, `npm test`, `npm run build`).
- **낡은 빌드를 보지 않는다.** `out/` 이 없거나 소스(`src`, `data`, `contract` 의 수집본·예시·데모 코드)보다 오래됐으면
  시험을 돌리지 않고 다시 빌드하라고 알린다. `npm run test:browser` 만 따로 돌릴 때를 위한 것이다.
- **끝나면 닫는다.** 서버와 브라우저는 시험 파일의 `afterAll` 이 닫는다. 시험이 실패해도 닫힌다. 시험이 만든 파일은
  운영체제의 임시 폴더에 두고 끝나면 지운다.

  - 브라우저가 문서를 통째로 되살리는 길(bfcache). 자동화 도구가 그 기능을 끄고 띄운다. 손으로 봤다(위 "`/view`").
  - HTTP 요청도 WebSocket 도 아닌 통신. 연 결과를 WebRTC(`RTCPeerConnection`)로 127.0.0.1 의 수신기에 보내려는 줄을
    넣어 보니 시험은 통과했고 수신기에는 연결이 닿았다(TCP 1개, UDP 3개). WebTransport 와 워커 안에서 여는 연결은
    넣어 보지 않았다. 소스 검사(`tests/commitments.test.ts`)의 목록에도 이 이름들은 없다(`ROADMAP.md` 의 8번과
    "사람 결정이 필요한 것").
  - Chrome 밖의 브라우저, 어두운 테마의 색(넘침은 색과 무관하다), 운영체제의 실제 끌어다 놓기와 파일 고르기 창,
    화면 낭독기. `/demo`·`/policy` 쪽과 `ROADMAP.md` 8번에 남은 확인은 아직 넣지 않았다.

## 상태가 정해지는 규칙 (`src/lib/report/status.ts`, `view-model.ts`)

| 조건 | 상태 |
|---|---|
| 발견의 outcome 이 `needs-review-uncertain` | 판단 보류(모름) |
| outcome 이 `needs-review` 이고 `ai_pending` 이 비어 있지 않음 | 검토 필요 · AI 확인 전 |
| outcome 이 `needs-review` 이고 `ai_pending` 이 비어 있음 | 미충족 신호(검토 필요) |
| 발견이 없고, v1 요약에서 `compliant > 0` | 충족 근거 발견 |
| 발견이 없고, v1 요약이 있음 (그 밖) | 적용 신호 없음 |
| 발견이 없고, 요약도 없고, 결과의 팩 판이 사이트의 팩과 다름 | 알 수 없음 |
| 발견이 없고, 요약도 없음 (`cli-0.3`, 팩 판이 같음) | 발견 없음 (AI 가 푼 경고가 있으면 그 사실을 대신 적는다) |

정책의 상태는 그 정책의 위치들 가운데 가장 먼저 봐야 할 것이다.

카드로 그리는 정책은 계약마다 다르다. `cli-0.3` 은 이 사이트의 팩에 실린 정책 전부에 결과에 나온 정책을 더한 것이고,
`v1-draft` 는 결과에 나온 정책(요약, 발견, AI 가 푼 경고)뿐이다. 그래서 `v1-draft` 에서 발견도 요약도 없는 카드(표의
마지막 두 줄)는 요약에 없는 정책이 AI 가 푼 경고에만 나오는, 손으로 만든 결과에서만 생긴다.

## 2층 설계 요약 (아직 만들지 않는다)

확장 구상에서 정한 방향이다. 만들기 전에 사실을 다시 확인한다.

1. 허용목록에 있는 GitHub 계정만 로그인한다(신원만, 권한 요청 없음).
2. 서버가 기본 브랜치의 커밋을 고정한다.
3. 일회용 격리 환경(Vercel Sandbox, 서울 리전, 영속 저장 끔)을 만든다.
4. 그 안에서 저장소 압축 파일을 받고 JS/TS 파일만 푼다. 경로 조작·심볼릭 링크·크기 상한을 막는다.
5. 받은 뒤 네트워크를 모두 끊는다.
6. `policypack scan --output-format json`(판정자 없음)을 돌린다.
7. 코드가 들어 있지 않은 필드만 골라 저장한다.
8. 환경을 파기하고 파기 시각을 남긴다.

검사를 Vercel 함수 안에서 직접 돌리지 않는 이유는 남의 코드를 격리할 수 없기 때문이다. 가장 가까운 선례는
Vercel Labs 의 deepsec(GitHub App + Sandbox)이다. 이 층을 시작하려면 `output: "export"` 를 걷어 내야 하고,
그것은 관문 G2 와 사람의 결정이 있어야 한다.
