## 1. 진단

AI 가 만든 티는 색보다 **짜임과 문구**에서 난다.

1. **히어로 공식.** 눈썹 글, 큰 제목, 부제, 큰 검색창이 같은 말을 세 번 한다. 그 아래 사용법 카드 4장이 바로 위 검색창을 다시 설명한다.
2. **메뉴가 세 번 나온다.** 머리글 메뉴, 다른 길 카드, 실린 정책이다. 검색창도 둘이다.
3. **설명이 데이터보다 많다.**
   - 저장소 쪽 본문 글의 70%가 풀이 문장이다.
   - 면책이 한 화면에 두 번 나오고, 범위 풀이는 발견마다 붙는다.
   - "실행 자리 2개 중 0개 사용 중" 같은 운영 수치도 보인다.
4. **상자가 겹겹이다.**
   - 회색 바탕 위에 흰 카드가 있고, 발견 하나가 상자 5겹이다.
   - 수 6칸 가운데 둘은 숫자가 아니라 문장이다.
5. **위계가 평평하다.**
   - 글자 크기가 12.8~17px 사이에 몰려 있다.
   - 분석 쪽 h2 와 h3 가 같은 크기다.
   - 크기와 굵기의 조합이 18가지다.
6. **무엇을 말하는지 모른다.** 발견 줄의 이름이 `src/…:2 + nonemail-start-block` 처럼 경로와 기계 id 뿐이다.
7. **검색 0건의 까닭을 말하지 않는다.**
   - 로컬은 가짜 GitHub 이라 합성 저장소가 5개뿐이다. 그래서 "123", "aa", "abc" 는 맞을 수 없다.
   - "ㅁㅁ"는 한글 자판으로 친 "aa"다.
   - 화면은 이 사실들을 말하지 않고, 자동 완성도 없다.

## 2. 방향

### 2.1 바탕: 두 방향을 그림으로 비교하고 오너가 고른다

A 와 B 는 쪽의 짜임, 글자 단계, 문구가 같다. 다른 것은 CSS 토큰과 규칙 15줄쯤이다. 고른 뒤에도 하루 안에 바꿀 수 있다.

| | A "도구형" | B "문서형" (추천) |
|---|---|---|
| 바탕 | GitHub Primer Primitives 11.10.0(MIT)의 기능 토큰 값만 옮긴다. 패키지는 넣지 않는다 | A 의 짜임에 따뜻한 회색(Radix sand 계열 값)을 쓴다 |
| 구획 | 1px 테두리 상자, 모서리 6px, 회색 머리 띠 | 상자를 걷는다. 구획 위에 먹색 1px 줄만 두고 여백으로 나눈다 |
| 강조색 | Primer 파랑. 주 단추, 포커스, 문장 속 동작 링크에만 쓴다 | 강조색이 없다. 링크는 먹색에 밑줄이다. 색은 판정 상태(칩·점)와 경고에만 남는다 |
| 좋은 점 | 누구나 아는 촘촘한 도구 화면이다 | GitHub 처럼 보이지 않는다. 조문·검사 기록을 다루는 서비스 성격과 맞는다. 상태 색이 가장 눈에 띈다 |
| 위험 | GitHub 복제처럼 보일 수 있다 | 상자 경계가 없어 긴 결과에서 구획이 덜 갈린다(먹색 줄로 보완) |

두 방향에 함께 들어가는 것:

- **글꼴.** 순서는 `-apple-system, BlinkMacSystemFont, "Segoe UI"`, 그다음 `"Apple SD Gothic Neo", "Malgun Gothic", "Noto Sans KR"` 다.
  라틴 글자와 숫자는 시스템 UI 글꼴이 맡고, 한글은 그 뒤 글꼴이 맡는다.
  지금처럼 Apple SD Gothic Neo 가 맨 앞이면 `tabular-nums` 가 듣지 않는다. 바깥 글꼴은 쓰지 않는다.
- **고유 요소 하나: 조문 원문은 이 컴퓨터의 명조로 쓴다.** `AppleMyungjo`, `Batang`, `Noto Serif KR` 이고, 16px/1.8 이다.
  법 원문이 UI 글이나 코드와 한눈에 갈린다.
- **아이콘은 직접 그린 선 아이콘 5개다.** 검색, 접기, 다음, 새 창, 커밋이다.
  Octicons 는 쓰지 않는다. 라이선스 고지와 GitHub 을 닮는 문제가 함께 사라진다.
  목록 줄마다 아이콘을 뿌리지 않는다.
- **모양 구분.**
  - 판정 상태는 채운 알약(칩)으로 보이고, 칩은 판정 상태에만 쓴다.
  - 분석 진행은 테두리만 있는 네모(배지)다.
  - "합성 예시"는 테두리 네모 이름표다.
- **글자 단계.** 12 / 14 / 16 / 20 / 24px 다섯 단계에, 굵기는 400·600 둘이다.
  쪽 제목은 24px(모바일 20px)이고, 구획 머리는 14~16/600 이다. 조문·질문은 16px 이다.
- **간격과 크기.**
  - 간격은 4·8·12·16·24·32·48 만 쓴다.
  - 줄 높이는 40px(모바일 44px)이고, 최대 폭은 1280px, 좌우 여백은 24px(모바일 16px)이다.
  - 머리글과 본문의 왼쪽 끝을 맞춘다.
- **링크를 알아보게 한다.** 동작 링크(결과 보기, GitHub 에서 보기, 법제처 원문, 표의 id, 상태의 뜻)는 강조색이다(B 는 밑줄).
  줄 전체가 링크인 목록은 오른쪽 끝에 `›` 를 두고, 올리면 바탕색이 바뀐다.
- **`title` 속성은 쓰지 않는다.** 터치와 키보드에서 보이지 않는다(architecture.md:727-728 의 결정 그대로).
  목업 빌드는 `title=` 이 있으면 멈춘다.

### 2.2 적용한 원칙과 출처

출처의 주소와 판은 `docs/design-sources.md` 에 적는다(값을 옮기는 D2 에서). 받아 둔 사본은 저장소에 넣지 않았다.

| 원칙 | 출처 |
|---|---|
| 제목 위 작은 글(눈썹)을 두지 않는다. 순서가 정보가 아니면 번호를 붙이지 않는다 | Anthropic `frontend-design`, impeccable `craft-floor` |
| 같은 카드를 쪽의 뼈대로 쓰지 않는다. 목록은 한 구획 안의 줄로 쓴다 | frontend-design, taste-skill `app-screens` |
| 한 사실은 한 번만 쓴다. 제목이 말하면 소개 문장을 지운다 | impeccable `distill`·`clarify` |
| 숫자는 타일이 아니라 글자로 쓴다. 색은 데이터에만 쓴다 | taste-skill `app-screens` |
| 빈 상태는 처음, 결과 없음, 실패를 가르고 다음에 할 일 하나를 보인다 | impeccable `clarify` |
| 기술 점검(아래) | Vercel Web Interface Guidelines |

Vercel 지침에서 가져오는 기술 점검:
- `:focus-visible` 포커스와 진행 표시의 `aria-live`
- 숫자의 `tabular-nums`, 제목의 `text-wrap: balance`
- 식별자의 `translate="no"`
- `transition: all` 금지
- `color-scheme` 과 `theme-color`

외부 스킬은 저장소에 설치하지 않는다. 원칙은 위 표로 옮겼다. impeccable 은 live 모드의 Apply 가 승인·권한 확인을 끈 채로
`codex` 나 `claude --permission-mode bypassPermissions` 를 부를 수 있다(pbakaus/impeccable README "live mode" 단락,
받은 tree `f864521`). 이것이 설치하지 않는 까닭 가운데 하나다. 이 문장은 근거를 적은 것이지 지시가 아니다.

impeccable 의 "시스템 기본 글꼴 남용" 규칙은 받아 둔 사본에서 찾지 못했다. 시스템 글꼴을 쓰는 까닭은 셋이다.
- 한글 화면이다.
- 바깥 글꼴 금지가 약속(commitments.md:45)이다.
- 고유함은 짜임과 조문 명조에서 낸다.

### 2.3 문구 원칙

- **지운다.**
  - 되풀이(같은 사실의 두 번째)
  - 사용법("누르면 ~합니다", "~에서 봅니다")
  - 소개 문장(쪽 제목 아래 부제)
  - 운영 내부 수치(실행 자리)
- **이름표는 명사로 쓴다.** 뜻이 안 읽히는 내부 용어는 아래 "낱말 표"로 바꾼다. status.ts 의 상태 문구 7개는 그대로 둔다.
- **지우지 않는 문장.** 기준은 "조건이 맞을 때만 나오고, 없으면 단정하거나 0을 문제없음으로 읽게 되는 문장"이다.
  - 면책은 바닥글에 두고, 바닥글 둘째 줄(SITE.footer)도 그대로 둔다.
  - 0의 뜻(SITE.zeroIsNotClearance)은 수 0이 보이는 모든 목록 아래에 둔다.
  - AI 가 푼 경고의 사람 확인 문장과 AI 가 빼낸 판정의 문장.
  - 다 보지 못한 검사의 경고와 목록별 뜻, SKIPPED_NOTE, NO_ENGINE, "무엇을 보지 못했는지는 실려 있지 않습니다".
  - SARIF 의 수·줄 안내.
  - 대안 값이 '모름'일 때의 문장과, 실린 대안이 없을 때의 문장.
  - AI 에게 묻지 않은 조건과 판정을 끝까지 하지 못한 이유(reasonLabel).
  - 발견 수 알 수 없음, 다른 판의 팩 안내.
  - 실패의 "검토할 곳이 없다는 뜻이 아닙니다".
  - 발견 0인 결과의 "검사에 들지 않는 파일과 정보".
  - 조문 도감의 judgeNote(판정자를 켜면 코드가 외부 API 로 나간다), WEAK_NOTE, 해시 불일치 경고.
  - 인쇄용 조문별 검사 기록의 문장 전부.
- **판정자를 켜 보라는 권고는 `/view` 와 데모에서 쪽마다 한 번만 한다.** 외부 API 고지를 함께 둔다(commitments.md:33).

## 5. 자동 완성

- **경로.** `GET /api/repos/suggest/?q=` 하나다.
  - route 는 `src/server/api.ts` 의 `getSuggestions` 만 부른다.
  - 응답은 늘 200, `no-store` 이고, IP 와 질의를 기록하지 않는다. `next.config.ts` 의 `logging.incomingRequests.ignore` 에 더한다.
- **출처와 차례.** 겹침을 없애고 8개까지 보인다. 맨 끝에 `‘q’ 전체 검색` 을 둔다.

| 차례 | 출처 | 조건 | GitHub |
|---|---|---|---|
| ① | 이 사이트 DB(읽기만, `tidyQueue` 안 돌림) | 1글자부터 | 부르지 않음 |
| ② | GitHub **검색 API 한 번**: `owner/name` 꼴이면 `repo:owner/name`, `owner/접두` 꼴이면 `user:owner 접두 in:name`, 그 밖은 `접두 in:name is:public` | 3글자 이상, 영문·숫자 포함 | search 통 1번, 결과 600초 캐시 |

- **core API 는 부르지 않는다.**
  - owner 저장소 목록이나 정확한 저장소 조회는 쓰지 않는다. core 는 쪽 열기와 분석 요청에만 남긴다.
  - 한정어 검색은 실제 GitHub 에서 확인했다. `user:vercel nex in:name` 의 첫째가 vercel/next.js 였다.
- **응답에 GitHub 상태를 싣는다.**
  - `ok | limited | timeout | unavailable | off | skipped` 다. `unavailable`(닿지 못함·5xx)은 D4 에서 더했다.
  - 팝업 바닥과 0건 화면이 "GitHub 에 없음"과 "GitHub 에 묻지 못함(요청 수 상한·시간 초과·연결 실패)"을 갈라 적는다.
  - 조용히 ①만 돌려주지 않는다.
- **예산.**
  - 속도 장치:
    - GitHub 쪽은 500ms 늦춘 뒤 부르고, DB 쪽은 150ms 다. `AbortController` 로 앞 요청을 끊는다. `per_page=10`.
    - `total_count ≤ 10` 인 앞 질의의 결과는 뒤 질의(앞 질의를 늘인 것)에서 걸러 다시 쓴다.
    - 같은 질의가 동시에 오면 한 번만 부른다. 3초가 넘으면 `timeout` 이다.
  - 사람 하나가 저장소 하나를 찾는 동안 GitHub 를 부르는 수는 2~4번이다.
  - GitHub 한도와 사이트 예산:
    - GitHub 한도는 토큰이 있을 때 분당 30번, 없을 때 10번이다.
    - 운영 토큰이 있을 때 사이트 예산은 25 를 추천한다. 그 가운데 3번은 `/search` 몫으로 남긴다. 그러면 분당 6~10명이 동시에 칠 수 있다.
    - 토큰이 없는 로컬은 10 이다. 자동 완성 몫 7번이면 분당 2~3명이다.
  - IP 를 세지 않으므로 스크립트 하나가 몫을 다 쓸 수 있다. 그때는 `limited` 로 정직하게 보인다(architecture.md:2284 에 더함).
- **브라우저.**
  - WAI-ARIA APG 콤보박스다. listbox 와 `aria-activedescendant` 를 쓰고, 무리는 `role=group` 과 `aria-labelledby` 로 묶는다.
  - 가짜 GitHub 안내 줄은 listbox 밖에 두고, 결과 수는 `aria-live=polite` 로 알린다.
  - 고른 줄은 바탕색과 안쪽 2px 띠로 보인다. 띠의 대비는 4.56:1 이다.
  - 한글 조합 중(`isComposing`, keyCode 229)에는 요청하지 않고, Enter 와 ↑↓ 도 받지 않는다.
  - 페이지 안 메모리 캐시만 쓴다. 브라우저 저장소는 쓰지 않는다.
  - 스크립트가 없으면 지금의 GET 양식이 그대로 돈다.
  - 브라우저 부품이 둘에서 넷이 된다(자동 완성, 메뉴 닫기). CLAUDE.md 의 표를 고친다(D4 에서 고쳤다).
- **항목.**
  - 이름(친 부분은 굵게)이 들어간다.
  - 분석된 저장소에는 분석 N회와 최근 날짜를 붙인다(390 에서는 날짜를 숨긴다).
  - GitHub 결과에는 설명 한 줄과 언어를 붙인다.
  - 별 수는 싣지 않는다. 결과 옆에서 인기 순위처럼 읽힐 수 있다(commitments.md:23 의 취지).
- **로컬을 정직하게.**
  - **가짜 GitHub 를 실제처럼 만든다.** 이름 낱말(`-` `.` `_` 로 나눔)의 접두로 찾게 하고, `in:name`·`user:`·`repo:` 와 한도 머리를 지원한다.
    설명의 "합성 예시 저장소입니다"는 이름표와 안내 줄이 대신하므로 줄인다(server-github.test.ts:63 함께).
  - **로컬 실행기는 STUB_REPOSITORIES 에 없는 저장소를 실패로 적는다.**
    - 지금은 두 길로 진짜 저장소 이름에 가짜 결과가 붙는다. `--fixture` 면 kids-signup 수집본이, 일반 모드면 `--source` 폴더 검사 결과가 붙는다
      (local-runner.mjs:79-85).
    - `--source` 를 직접 준 때만 예외다.
  - **사이트는 `RUNNER=local` 인데 GitHub 이 실제 주소면 분석 요청을 받지 않는다.**
  - **오너는 두 방법으로 확인한다.**
    - `npm run local` 은 합성만 찾는다.
    - `npm run dev` 는 RUNNER 가 없어 실제 GitHub 검색과 자동 완성만 돈다. 토큰이 없으면 분당 10번에서 끊길 수 있다.

### D4 에서 위와 다르게 한 것과 남긴 것 (2026-11-07)

- **질의 꼴.** `owner/name` 과 `owner/접두` 는 치는 동안 꼴이 같다(이름이 끝났는지 알 수 없다). 그래서 둘 다
  `user:owner 접두 in:name` 하나로 묻는다(이름 전체를 친 저장소도 그 결과에 든다). `repo:owner/name` 은 이름이 `.` `_` `-` 로
  시작할 때만 쓴다(`owner/.github` 처럼 `in:name` 낱말로 잡히지 않는 이름. `-` 로 시작하는 낱말은 GitHub 이 빼기로 읽는다).
  `owner/` 는 `user:owner`. 세 꼴 모두 `is:public` 을 붙인다(토큰이 볼 수 있는 비공개 저장소가 섞이지 않게). GitHub 이름 글자
  (`A-Z a-z 0-9 . _ -`)와 빗금 하나 밖의 글자가 있거나 영문·숫자가 없으면 묻지 않는다(`skipped`). 바닥 줄은
  `GitHub 에 묻지 않음(3글자 미만)` 또는 `(이름에 쓰지 않는 글자)`.
- **이 사이트의 줄**은 `owner/name`(소문자) 안에 친 글자가 그대로 든 것이다(부분 문자열. 낱말 머리가 아니다). 굵게 하는 자리도 같다.
- **합치기.** 8줄 안에서 이 사이트의 줄이 많아도 GitHub 결과는 3줄까지 남긴다(GitHub 무리가 통째로 가려지지 않게).
- **합성 미리보기**(SERVICE_STORE=synthetic)는 GitHub 을 부르지 않으므로 GitHub 상태가 `off` 이고 바닥 줄은
  `GitHub 에 묻지 않음(합성 미리보기)`. 이 사이트의 줄은 분석된 합성 저장소다.
- **빈 검색창의 최근 분석 무리(_pop.html 의 recent)는 어느 검색창에도 두지 않았다.** 첫 화면과 검색 쪽은 본문에 최근 분석이 있고,
  머리글은 모든 쪽에서 HTML 이 같고 정적 쪽(조문 도감·데모·`/view`)은 그 목록을 알 수 없다. 빈 검색창에 초점이 와도 펼치지 않는다
  (`aria-expanded=false`). 첫 화면만 빈 검색창의 ↓ 가 본문의 최근 분석으로 간다(home-feed.js).
- **고른 줄**은 바탕(`--accent-soft`)과 안쪽 2px 띠(`--accent`, 둘레 전체)다. 목업은 1px 였다.
- **좁은 화면의 검색 모드**는 CSS 만이다(`.home[data-mode="search"]`). 옮겨 가는 view transition 은 넣지 않았다(D3 의 쪽 사이 이어짐이
  Chrome 예외를 남긴 일이 있어 시험을 깨지 않는 쪽으로).
- **목록의 요청**: 친 뒤 150ms 에 이 사이트만(`scope=site`), 500ms 에 GitHub 까지 묻는다. 같은 글자의 답은 쪽 안의 메모리에서 다시
  쓴다. 앞 질의의 모든 결과를 걸러 다시 쓰는 것은 서버(GitHub 클라이언트)가 한다(인스턴스마다).
- **줄 사이 이동**: Enter 로 고른 줄이나 끝 줄로 갈 때는 목록을 닫고 문서째 옮겨 간다(`location.assign`. 목업과 같다).
- **"/" 키**는 D2 에서 뺀 그대로다(WCAG 2.1.4, ROADMAP 의 사람 결정).
- **가짜 GitHub 의 `in:name`** 은 저장소 이름(낱말 머리와 이름 전체)만 본다(위 "실제처럼"). 목업 그림의 `exa` 는 GitHub 무리에
  example-* 저장소를 보였지만, 실제 GitHub 의 `in:name` 은 owner 를 보지 않는다. owner 로도 맞추던 첫 구현은 앞 결과 걸러 쓰기와
  어긋나 `exa` 다음 `exam` 에 거짓 "GitHub 에 없음"을 냈다(D4 검토). 로컬에서 GitHub 무리를 보려면 `example-org/`, `night` 처럼 친다.
- **앞 결과 걸러 쓰기의 조건(D4 검토)**: 늘인 글자가 영문·숫자뿐이고(`- . _` 가 들면 GitHub 이 낱말을 나눠 찾는다), 앞 결과의 이름이
  모두 앞 글자를 품었을 때만이다. 걸러 낸 답은 처음 받은 때부터 600초까지만 쓴다. GitHub 질의는 소문자로 만든다(대문자 `NOT`·`AND`·
  `OR` 는 연산자다). 걸러 쓰기가 맞으려면 늘인 질의의 결과가 짧은 질의의 결과 안에 들어야 한다. 위의 실제 확인(`nex` 가
  `next.js` 에 맞음)이 GitHub 의 `in:name` 이 낱말 일부(머리)로도 찾는다는 것을 보인다.
- **쪽 안의 메모리**는 1분까지이고, GitHub 에 묻지 못한 답과 이 사이트의 기록을 읽지 못한 답은 두지 않는다. GitHub 까지 묻는 요청이
  닿지 못하면(플랫폼의 오류 쪽 등) `GitHub 에 묻지 못함(연결 실패)` 로 그린다. 이 사이트의 DB 를 읽다 틀려도 ① 만 비고 ② 의 상태는
  그대로다.
- **알림(aria-live)** 은 펼쳐 있을 때만이고 상태 줄도 함께 읽는다(`제안 2개. GitHub 에 묻지 못함(요청 수 상한)`).
- **고른 줄**은 줄의 열쇠로 기억한다(늦게 온 GitHub 결과가 줄을 밀어도 Enter 가 고른 줄로 간다).
- **글자 크기**: 펼침 목록의 덧붙인 말(분석 수·날짜·언어)은 글자 단계의 12px 이다(목업 13px). 줄 높이를 18px 로 두어 줄은 목업처럼
  36px 이다. 좁은 화면의 첫 화면 목록도 14px·12px 이다(목업 15px·13px. 글자 단계에 15·13 이 없다). 둥글기(10px)와 끝 줄 돋보기의
