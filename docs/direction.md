# 방향 B — 공개 저장소 분석 서비스 (2026-10-24 오너 결정)

이 문서는 오너가 2026-10-24 에 정한 새 방향과 그 설계 초안이다. 규칙 파일(`CLAUDE.md`, `docs/commitments.md`)을 바꾸는
안은 `docs/proposals/2026-10-24-rules.md` 에 있고, 오너가 반영하기 전까지는 지금 규칙(1층)이 그대로 유효하다.

## 한 문장

GitHub 공개 저장소를 검색해 들어가면, 누군가 이미 요청한 분석 결과를 누구나 보고, 없거나 다시 보고 싶으면 분석을
요청하며, 분석 중이면 진행 과정이 모두에게 보이는 웹. 분석 결과 쪽은 정책 검토 지점을 분석적이고 단정하게 한눈에 보인다.
기말 발표(12/15~21)에서 실제로 접속해 분석 요청을 시연하고, 이미 분석된 저장소의 결과를 보여 준다.

## 오너가 정한 것 (2026-10-24)

| 물음 | 결정 |
|---|---|
| 결과를 누가 보나 | 누구나 본다. 숨김 장치는 두지 않는다 |
| 서버에서 AI 판정자를 켜나 | 늘 켠다(분석에는 AI 가 반드시 함께 돈다). 화면에 그 사실을 따로 알리지 않아도 된다 |
| 분석 요청에 로그인이 필요한가 | 필요 없다. 누구나 요청한다 |
| 분석을 어디서 돌리나 | GitHub Actions(매번 새 VM) |

않음)을 `/view`·`/demo` 와 함께 쓴다.

## 구조

```
브라우저 ──▶ Next.js (Vercel, 서버 포함)
              ├─ GitHub 검색: 서버가 GitHub API 를 대신 부른다(토큰은 서버에만, 짧게 캐시)
              ├─ 분석 요청: 제한 검사 → DB 에 분석 행(queued, 대기열) → 실행 자리가 비면 깨우기
              ├─ 깨우기(대기열 넘기기): 실행 자리(POOL_SIZE)가 빈 만큼 먼저 요청한 것부터 dispatched 로 표시하고
              │    GitHub Actions workflow_dispatch(분석 id). 요청·콜백·읽기 때마다 한다. 상태는 DB 에만 둔다.
              │    깨우지 못하면 대기열에 되돌리고 2분 쉰다(runner_wake). 주기적으로 깨우는 것은 아직 없다
              ├─ 진행·결과 읽기: DB. 진행 중인 쪽은 몇 초마다 다시 읽는다(대기열의 몇 번째인지도)
              └─ 실행기 콜백: 서명한 요청만 받아 진행 단계와 결과를 적는다 → 끝나면 다음을 깨운다
Postgres ── analyses(id, owner, repo, commit, status, step, 시각, 보낸 시각, 도구 판, 팩 판, 오류, review 계획), results(분석 id, CLI JSON, 프로필, review),
              github_budget(GitHub 을 부르는 수의 1분 창. 서버 인스턴스가 함께 쓴다),
              runner_wake(실행기를 깨우지 못한 마지막 때와 까닭. 한 행)
GitHub Actions(실행기 저장소) ── 공개 저장소를 그 커밋으로 받음 → CLI 설치(고정 커밋) →
              policypack scan --judge anthropic:<모델> --output-format json → profile → review(REVIEW 켜짐) → 단계마다 콜백 → 결과 콜백
(그림: /how 의 그림 1)
```

- 분석 id 는 추측하기 어려운 짧은 id 로 하고, 같은 저장소를 여러 번 분석해도 분석마다 따로 남는다.
- 진행 단계: 대기 → 저장소 받기·도구 설치 → 검사(정적 검사와 AI 판정) → 정리 → 완료(또는 실패와 그 까닭). 처음 안은 정적
  검사와 AI 판정을 두 단계로 나눴지만, 실행기는 CLI 명령 하나(`policypack scan … --judge anthropic:<모델>`)를 부르고 CLI 는 둘의
  경계를 알려 주지 않는다(결과에는 걸린 초만 있다). 그래서 한 단계로 적는다(B2 차례 B, 2026-11-03). 판정자가 무엇이었는지는
  결과의 `run.judge` 가 말한다.
- 남용과 비용 막기(로그인이 없으므로 기본값으로 둔다. 값은 오너가 바꿀 수 있다): 같은 저장소·같은 커밋에 분석이
  진행 중이거나 최근(예: 1시간) 끝났으면 새로 만들지 않고 그 분석으로 보낸다, 하루 전체 분석 수 상한, 동시에 도는 분석
  수 상한(실행 자리 수. 넘는 요청은 거절하지 않고 대기열에 둔다. 대기열 길이에도 상한), 저장소 크기·JS/TS 파일 수 상한,
  실행 시간 상한, Anthropic 콘솔의 월 지출 상한.
- 실행기는 대상 저장소의 코드를 실행하지 않고 읽기만 한다. 비밀값은 Actions 의 secret 에만 둔다.

**B1 결과 (2026-10-24):** 첫 화면(온보딩·검색창·최근 분석), 검색(`/search/?q=`, 브라우저에서 합성 목록을 거름), 저장소(`/r/{owner}/{repo}/`, 분석 기록·진행 중인 분석·누를 수 없는 요청 단추), 분석(`/r/{owner}/{repo}/a/{id}/`, 진행 중·대기·실패의 단계 표와 끝난 분석의 대시보드·조문별 검사 기록)을 합성 저장소 여섯·분석 아홉으로 만들었고, 375·1280px 의 두 테마에서 넘침·대비·바깥 요청을 브라우저 시험이 본다. 데이터는 `src/lib/service/` 의 `ServiceStore` 인터페이스 뒤에 있고 B1 은 합성 구현(`synthetic.ts`)이라, B2 에서 `index.ts` 의 한 줄을 Postgres·GitHub 검색 구현으로 바꿔 끼운다. 끝난 합성 분석의 결과는 `contract/cli-current` 의 판정자 없는 실제 출력이라 AI 판정 단계를 "건너뜀"으로 적고, 합성 저장소에는 GitHub 주소가 없어 파일·줄·커밋 링크를 걸지 않는다(링크는 저장소 주소가 있을 때만 만들고 부품 시험이 본다).

**B1 검토 반영 (2026-10-25):** 발견이 있는 정책 카드에 근거 조문 원문(`legal[].text`, 대표 조문)을 접어 두었다. 발견이 없는 정책은 카드 대신 표 한 장에 모으고 상태의 뜻을 상태마다 한 번 적는다. 한눈에 보는 수를 대시보드 맨 위로, 진행 기록을 맨 아래로 옮겼다. 저장소 쪽 분석 목록에 0건이 있으면 0의 뜻을 적는다. 분석 쪽의 정책 카드는 판정자를 켜 보라고 권하지 않는다(권하는 자리는 `/view` 뿐). 실패한 분석의 시작하지 않은 단계는 "하지 않음", 대기 중인 분석의 대기 단계는 "대기 중"이다. 요청 단추는 `aria-disabled` 라 키보드로 닿는다. 검색 쪽에서는 머리글 검색창을 화면에서 감춘다(HTML 은 모든 쪽에서 같다). 조문별 검사 기록은 결과 JSON 에 없는 커밋과 검사한 날을 분석 기록에서 채우고 이름에 "(분석 기록)"을 붙인다(결과에 커밋이 있으면 결과의 것). 검사한 날은 정적 검사 단계가 시작한 시각이다.

**B1 정확성 검토 반영 (2026-11-03):** 결과가 없거나 읽지 못한 끝난 분석은 저장소 쪽 목록과 첫 화면에서 "발견 0건"이 아니라 "발견 수 알 수 없음"이다(0의 뜻도 적지 않는다). 분석 중인 분석이 단계 사이에 있으면 목록에 "대기 중"이 아니라 "다음 단계 기다림"이다. 실패한 단계에 끝난 시각이 없으면 멈춘 시각과 걸린 시간을 적지 않는다. 결과가 다른 판의 팩으로 만들어졌으면 대시보드에 이 사이트의 팩 조문 원문을 싣지 않는다. `npm run check` 통과(부품 시험 1263, 브라우저 시험 174), 375px 어두운 테마와 1280px 밝은 테마로 새 쪽을 열어 확인했다.

**B2 차례 A (2026-11-03, 서버 토대):** 정적 내보내기(`output: "export"`)를 걷고, 서버 코드를 `src/server/`(설정·DB·GitHub·저장소 구현·실행기 깨우기)에 두었다. DB 는 `DATABASE_URL` 이 있으면 Postgres(`pg`), 없으면 PGlite(`.data/pglite`)이고 같은 마이그레이션 SQL 을 쓴다. 분석 서비스의 네 쪽은 요청 때 그리고(`SERVICE_STORE=synthetic` 이면 B1 의 합성 저장소), 검색은 서버가 GitHub 검색을 부른다. 분석 요청(같은 커밋으로 보내기, 하루·동시 상한, 크기 상한, 실행기 깨우기)과 오래된 분석의 시간 초과는 저장소 구현에 있고 시험이 보지만, 요청을 받는 `/api/` 와 실행기 콜백, 화면의 요청 단추·진행 다시 읽기는 다음 차례다.

**B2 차례 B (2026-11-03, 요청·실행기·콜백):** `POST /api/analyses/`(요청), `GET /api/analyses/{id}/`(진행), `POST /api/runner/{id}/`(실행기 콜백: 단계 시작·결과·실패), `POST /api/runner/claim/`(로컬 실행기가 대기 중인 분석을 집어 감)를 두었고, 콜백은 `RUNNER_SECRET` 으로 HMAC-SHA256 서명한 요청만(시각 어긋남 5분까지) 받으며 단계는 차례대로만, 끝난 분석은 바뀌지 않는다. 실행기는 `.github/workflows/analyze.yml` + `runner/run.mjs`(Node 내장 모듈만: tarball 받기·안전하게 풀기, JS/TS 파일 수 상한, CLI 고정 커밋 설치, 검사, 결과 크기 상한)이고, `scripts/local-runner.mjs --fixture` 가 같은 코드로 이 컴퓨터에서 요청부터 결과까지 돌린다. 정적 검사와 AI 판정은 CLI 가 경계를 알려 주지 않아 한 단계 "검사(정적 검사와 AI 판정)"로 합쳤다(위 "진행 단계").

**재디자인 D4 (2026-11-07, 자동 완성):** `GET /api/repos/suggest/?q=`(늘 200, `no-store`)를 더했다. 이 사이트 DB 의 분석된
저장소(owner/name 에 친 글자가 든 것)와 GitHub 검색 API 한 번(3글자 이상, 이름 글자만. core 는 부르지 않는다)을 합쳐 8줄까지
돌려주고, GitHub 상태(`ok | limited | timeout | unavailable | off | skipped`)를 싣는다. 검색 예산은 검색 쪽과 함께 쓰고 검색 쪽 몫
(`GITHUB_SEARCH_RESERVE`)을 남긴다. 브라우저 부품은 요청 단추·진행 다시 읽기·검색창(자동 완성)이고 모두 같은 사이트의 `/api/` 만
부른다(머리글의 메뉴 닫기 부품은 어디에도 요청하지 않는다). 자세한 것은 `docs/redesign.md` 5장과 `docs/architecture.md`.

**B2 차례 C (2026-11-03, 쪽 연결·진행 표시):** 저장소 쪽의 요청 단추가 `POST /api/analyses/` 를 불러 새 분석이나 같은 커밋의 분석 쪽으로 가고, 받지 않으면 서버가 돌려준 까닭(하루·동시 상한, 크기, 없음, 실행기 없음)을 단추 옆에 그대로 적으며, 누르는 동안은 다시 누를 수 없다. 진행 중인 분석 쪽은 `GET /api/analyses/{id}/` 를 3초마다 읽어 머리와 단계를 다시 그리고(탭이 숨으면 쉬고), 끝나거나 실패하면 읽기를 멈추고 같은 문서에서 서버가 새로 그린 대시보드나 멈춘 단계와 까닭을 받는다. 브라우저 시험이 `next start` + PGlite + 가짜 GitHub 에서 단추 → 로컬 실행기(`--fixture`) → 단계가 바뀌는 진행 표시 → 대시보드를 한 바퀴 돌고, 거절·연결 실패·두 번 누름·탭 숨김·실패 콜백과 375px 두 테마의 넘침·대비를 본다.

**B2 검토 1 반영 (2026-11-03):** 한 사람이 사이트의 GitHub 요청 수 상한을 다 쓰지 못하게 끝 커밋을 30초 두고 GitHub 을 부르는 수에 서버 인스턴스마다 1분 예산을 두었다(요청한 사람은 세지 않는다). 실행기 콜백은 본문에 실은 저장소·커밋이 분석 행과 같아야 받고, 워크플로는 콜백 주소의 출처를 Actions 변수 `SITE_URL` 과 견주며, CLI 의 딸린 꾸러미는 고정한 날짜까지의 판에서만 고른다. 그 밖에 서명 머리를 본문보다 먼저 보고, `pg` Pool 의 오류를 듣고, 발견 수를 결과를 받을 때 적어 두고, 긴 검색어가 좁은 화면에서 넘치지 않게 했다(`architecture.md` 의 "검토 1 반영"). 실제 Postgres 의 동시 경합 시험은 Postgres 가 없어 아직이다(`ROADMAP.md`).

**B2 대기열 (2026-11-03, 오너 제안):** 동시 상한을 넘는 요청을 429 로 거절하던 것을 대기열로 바꿨다. 요청은 (같은 커밋으로
보내기, 하루 상한, 크기 상한을 지나면) 늘 대기열에 받고, 실행 자리(`POOL_SIZE`, 옛 `CONCURRENT_LIMIT`)가 비면 먼저 요청한
것부터 실행기를 깨운다. 깨우는 때는 요청·실행기 콜백·쪽과 진행 읽기·로컬 실행기의 집어 가기이고, 자리 세기와 고르기는 DB 의 권고
잠금과 `UPDATE … WHERE dispatched_at IS NULL … RETURNING` 으로 하므로 서버 인스턴스가 여럿이어도 한 분석을 두 번 보내지 않는다.
대기열이 `QUEUE_LIMIT` 이면 그때만 429 다. 보낸 뒤 실행기가 시작을 알리지 않으면(`DISPATCH_TIMEOUT_MINUTES`), 대기열에서 너무 오래
기다리면(`QUEUE_TIMEOUT_MINUTES`) 까닭과 함께 실패로 적고, 실행 시간 상한은 보낸 때부터 센다. 대기 중인 분석 쪽·저장소 쪽·요청
단추가 대기열의 몇 번째인지와 실행 자리를 DB 에서 센 숫자로 적는다(재디자인 D3, 2026-11-07 부터 실행 자리의 수는 화면에서 뺐다.
대기 중일 때 대기열의 몇 번째인지만 적고, 다시 읽지 않는 저장소 쪽은 `HH:MM KST 기준` 을 붙인다). GitHub 을 부르는 수의 예산도 DB 의 1분 창 카운터로 옮겨 서버
인스턴스가 함께 쓴다(캐시는 인스턴스마다). `docs/architecture.md` 의 "대기열과 실행 자리". 검토 뒤(같은 날): 깨우기에 실패하면
분석을 실패로 적지 않고 대기열에 되돌린 뒤 2분 동안 깨우지 않는다(실행기 장애가 이어질 때 읽을 때마다 하나씩 실패하지 않게).
정리는 "실행·보냄 시간 초과 → 넘기기 → 대기 시간 초과" 차례이고, 대기 시간 초과의 까닭에는 그때 센 사실만 적는다.

### 기본 제한 값 (환경 변수로 바꾼다. `src/server/config.ts`)

| 환경 변수 | 기본값 | 뜻 |
|---|---|---|
| `MAX_REPO_KB` | 100000 | 받는 저장소 크기 상한(KB, GitHub 의 `size`. 기록까지 센 값이라 받는 압축 파일보다 크다) |
| `DEDUPE_MINUTES` | 60 | 같은 커밋의 분석이 이 시간 안에 끝났으면 새로 만들지 않고 그 분석으로 보낸다(대기·진행 중이면 늘 그 분석으로) |
| `DAILY_LIMIT` | 30 | 하루(한국 표준시 0시~) 새로 만드는 분석 수 |
| `POOL_SIZE` | 2 | 실행 자리 수: 실행기에 보냈거나 분석 중인 분석 수의 상한(동시에 도는 분석 수). 넘는 요청은 거절하지 않고 대기열에 둔다. 비우면 옛 이름 `CONCURRENT_LIMIT` 을 읽는다 |
| `QUEUE_LIMIT` | 20 | 대기열(실행기에 보내기 전)의 길이 상한. 넘으면 그때만 요청을 받지 않는다(429) |
| `RUN_TIMEOUT_MINUTES` | 32 | 실행기에 보낸 뒤 이 시간을 넘게 끝나지 않은 분석은 "시간 초과"로 실패 처리한다(요청한 때가 아니라 보낸 때부터 센다. 워크플로의 `timeout-minutes` 는 30) |
| `DISPATCH_TIMEOUT_MINUTES` | 10 | 실행기에 보낸 뒤 이 시간 안에 실행기가 시작을 알리지 않으면 실패로 적고 다음을 보낸다 |
| `QUEUE_TIMEOUT_MINUTES` | 120 | 대기열에서 이 시간을 넘게 실행 자리를 기다린 분석은 까닭과 함께 실패로 적는다 |
| `SEARCH_CACHE_SECONDS` | 60 | 같은 검색어의 GitHub 검색 결과를 서버 메모리에 두는 시간 |
| `SUGGEST_CACHE_SECONDS` | 600 | 자동 완성(`GET /api/repos/suggest/`)의 GitHub 검색 결과를 서버 메모리에 두는 시간 |
| `REPO_CACHE_SECONDS` | 300 | 저장소 정보를 서버 메모리에 두는 시간 |
| `COMMIT_CACHE_SECONDS` | 30 | 기본 브랜치 끝 커밋을 서버 메모리에 두는 시간(같은 저장소의 요청이 잇따라도 GitHub 을 한 번만 부른다) |
| `GITHUB_SEARCH_PER_MINUTE` | 10 | 이 사이트가 1분에 GitHub 검색을 부르는 수(검색 쪽과 자동 완성이 함께 쓴다). **`GITHUB_TOKEN` 이 있으면 기본 25.** 서버 인스턴스가 DB 의 1분 창 카운터를 함께 쓰고(DB 에 닿지 못하면 인스턴스마다 센다), 요청한 사람을 가리지 않는다. 넘으면 "요청 수 상한"으로 답한다(GitHub 은 토큰 없이 1분 10번, 토큰으로 30번) |
| `GITHUB_SEARCH_RESERVE` | 3 | 그 가운데 검색 쪽(`/search`) 몫. 자동 완성은 1분 창에 쓴 수가 `GITHUB_SEARCH_PER_MINUTE - 이 값` 보다 적을 때만 GitHub 을 부르고, 검색 쪽은 상한까지 부른다. 늘 상한보다 작게 읽는다(같거나 크면 상한-1) |
| `GITHUB_CALLS_PER_MINUTE` | 60 | 이 사이트가 1분에 검색 밖의 GitHub API(저장소 정보·끝 커밋)를 부르는 수(GitHub 은 토큰으로 1시간 5000번) |
| `RESULT_MAX_KB` | 4000 | 실행기가 보내는 결과 JSON 의 크기 상한(KB). 넘는 콜백은 받지 않는다(Vercel 함수의 본문 상한 4.5MB 보다 작게) |
| `RUNNER` | none | `github`(workflow_dispatch), `local`(이 컴퓨터의 로컬 실행기가 집어 감), `none`(요청을 받지 않음) |
| `REVIEW` | 끔 | `on` 일 때만 실행기가 검사 뒤에 `policypack review` 도 돌린다(모델 호출, 한 건의 금액·시간 상한은 워크플로의 `REVIEW_*`). 같은 커밋의 저장된 review 가 있으면 돌리지 않고 그것을 쓴다. 켜는 것은 오너가 비용을 정한 뒤다(2026-11-12 오너 승인, 배포에서 켬) |
